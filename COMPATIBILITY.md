# Compatibility

Upstream parity target: [tester-army/e2e](https://github.com/tester-army/e2e) commit `ee901b333ed12352418dfb07bda5eafe32e71c8d` (`docs(agents): show several personas running one suite (#1258)`). On 2026-10-19 the 300 upstream commits from `94ddbfe` to it were checked: each commit's title and release note against this file, and against the port's code where the note named a behavior. A commit that only changes docs, tests of code the port lacks, dependencies, or release notes needs no entry. The sections were not re-read line by line against upstream's source, so a statement that no commit in that range touched is as it was at `94ddbfe`. The packages upstream has are in [Upstream packages](#upstream-packages).

Names are C# versions of the JavaScript API: `agent.act` is `ActAsync`, `screen.getByRole` is `GetByRole`, `expect(locator).toContainText` is `Expect.That(locator).ToContainTextAsync`, and `unique()` is `Values.Unique`.

## Ported

- NUnit `[Test]`, `[SetUp]`, `[TearDown]`, `[OneTimeSetUp]`, and `[OneTimeTearDown]`
- `Assert.Ignore`, `[Retry]`, `[Timeout]`, and `[Category]`
- Screen queries: role, text, label, test id, placeholder, display value, `filter` (`hasText`, `hasNotText`, `has`, and `hasNot`), `or`, `first`, `last`, `nth`. A locator offers every query kind, scoped to its matches' descendants. Every query takes a `TextMatch`: a string or a .NET `Regex`, tested against the whitespace-normalized text. A string matches the whole text, case-sensitively, unless `exact` is false, which makes it a case-insensitive substring, as upstream. `RoleOptions` carries `name`, `checked`, `disabled`, `selected`, `expanded`, `pressed`, and `level`, and `img` is read as `image`. A role query never matches a hidden node; the other kinds keep hidden nodes unless `Visible` is set, as upstream. `getByLabel` matches any node whose accessible name matches, as the upstream reference resolver does. Options are C# objects (`RoleOptions`, `TextMatchOptions`) instead of object literals, and `filter({ hasText, hasNotText, has, hasNot })` is the overloads `Filter(TextMatch)` and `Filter(Locator)` plus `Filter(hasText, hasNotText, has, hasNot)`, whose four parameters are optional and named (.NET-only: the named-argument form of upstream's options object). `hasNotText` (tester-army/e2e#1037, `a481fd3`) drops a match whose subtree text matches, with `hasText`'s substring rules (an empty string matches everything, so it drops every match). `hasNot` (#1334, `6c8e71f`) drops a match whose subtree resolves the inner locator, resolved inside each match as `has` is, and a display-value `hasNot` is `UNSUPPORTED_CAPABILITY` in the core resolver as `has` is. A `Filter()` with none of the four is `INVALID_LOCATOR` (`filter() requires hasText, hasNotText, has, and/or hasNot`). Upstream's refusal of an unknown key (`visible`) or a non-object options has no port, since the parameters are typed. On iOS a plain React Native `View` has no children in the tree, so `hasNot` keeps every such row (see the mobile guide) Regular expressions use .NET syntax, not ECMAScript. `GetByTestId` also takes `Exact`, which upstream's `getByTestId` does not. `locator.or(other)` (upstream #1049) is `Or(Locator)`: a `union` expression that matches either branch once, in document order, and stays strict (`STRICT_MODE` where upstream says `LOCATOR_AMBIGUOUS`; add `First()` when both may match). Both locators must come from the same screen and attempt, else `INVALID_LOCATOR`. `LocatorResolver.Resolve` and `DeviceLocator.ResolveExpression` resolve the union. Differences: the parameter is typed, so upstream's refusal of a non-locator has no port (`null` is an `ArgumentNullException`); and upstream's `UNSUPPORTED_CAPABILITY` for a display-value branch has no port, since the port's engines resolve over their tree. Web branches with different frame-selector chains fail with `UNSUPPORTED_CAPABILITY` (`locator.or requires both branches in the same document`) as upstream's `frameSelectors` does
- Actions: tap, click (an alias of tap), doubleTap (`DblClickAsync` is an alias), fill (a string or a `Secret`), pressSequentially, press, check, uncheck, clear, selectOption, focus, scrollIntoView. They wait up to the action timeout for exactly one enabled, visible match. `selectOption` takes a string that matches an option value or label. `ActionOptions.Timeout` overrides the wait per action (`PressSequentiallyOptions` adds `Delay`). The web engine's own Playwright wait still uses the configured action timeout
- Locator reads: `textContent`, `inputValue`, `getAttribute`, `isVisible`, `isHidden`, `isEnabled`, `isDisabled`, `isChecked`, `boundingBox`, `count`, `all`, `allTextContents`. A read of one node (`textContent`, `inputValue`, `getAttribute`, `isEnabled`, `isDisabled`, `isChecked`, `boundingBox`) waits for its one match until the action timeout, then reads once with no retry for a value; `isVisible`, `isHidden`, `count`, `all`, and `allTextContents` answer from the current screen at once. No read verifies an earlier `act`. `textContent` and `allTextContents` collapse each whitespace run to one space and trim, as upstream. A single-node read fails with `NOT_FOUND` when nothing matches before the action timeout ends
- `screen.tree()` and `screen.debug()` (commit `d7ec0ec`) are `Screen.TreeAsync` and `Screen.DebugAsync`. One observation of the whole screen, rendered by `FailureEvidence.Listing` (the trace's screen at failure, upstream's `prepareObservation`): one node per line, children indented, secrets redacted, cut at the observation byte limit (262144). A node the page does not show is left out. A step of kind `screen`. `DebugAsync` writes the text to `Console.Out`, where a test framework picks it up. Differences: `Timeout` bounds the read with a linked token and fails with `OPERATION_TIMEOUT`, where upstream passes it to the engine operation. A `Locator` has no `TreeAsync`, so upstream's refusal on a locator is a compile error. On a `FrameScreen` they refuse with `INVALID_ARGUMENT`, as upstream's do. The same commit's change to print test output without the `list` reporter, and to keep stdout for `--reporter json`, is not ported: the port has no runner. `screen-tree.test.ts` is `ScreenTree/ScreenTreeTests` and `ScreenDebugTests` (not ported: the refusal on a locator, the unknown option, and `sdk-types.ts`'s checks, which a typed API makes compile errors); `screen-tree-secrets.test.ts` is `ScreenTreeSecrets/ScreenTreeTests` (through a session over a fake engine). `run-user-output.test.ts`'s two new cases are not ported with the runner change.
- `screen.scrollUntilVisible` and `locator.scrollUntilVisible` (`locator/screen.ts`) are `Screen.ScrollUntilVisibleAsync` and `Locator.ScrollUntilVisibleAsync`, with `ScrollUntilVisibleOptions { Direction, Momentum, Timeout }` (down, slow, 30 s by default). `Momentum` (`None`, `Slow`, `Fast`; upstream's `Momentum`) moved from `E2E.Mobile` to `E2E.Engine` beside `ScrollDirection`, and `LocatorAction.Swipe` carries it. `IEngineSession.SwipeAsync(direction, momentum, ct)` is the viewport swipe with a stride; its default drops the momentum. `WebEngine` strides as upstream's `swipeDistance` (none half, slow three quarters, fast one and a half of the extent; a swipe naming none keeps three quarters), `MobileEngine` strides a node swipe by it and keeps the device client's default for the whole-screen swipe, and `DocumentEngine` and `WinAppEngine` have one stride. The port has no operation context, so a swipe's deadline is the cancellation of the token it runs under, and a swipe the deadline ends fails with an `OPERATION_TIMEOUT` cause. A locator swipe's engine error is not wrapped in `ACTION_FAILED`, since the port has no `translateLocatorError`. `filter({ has })` now refuses a locator of another screen with `INVALID_LOCATOR`, as upstream's `ownLocator` does
- `locator.waitFor` with `attached`, `detached`, `visible` (default), and `hidden`, as `WaitForAsync(new LocatorWaitForOptions { State, Timeout })`. The timeout defaults to the action timeout. `LocatorWaitForOptions` is named apart from `agent.waitFor`'s `WaitForOptions`. Differences: a timeout fails with `TIMEOUT` (upstream `LOCATOR_NOT_FOUND`, `locator did not become <state>`), and a passing `waitFor` does not verify an earlier `act` (upstream it does). The timeout carries `Details` as upstream's does (the locator, what it asked for, and how long it waited; see [Trace page](#trace-page))
- Locator expectations: visible, hidden, attached, enabled, disabled, checked, selected, expanded, focused, text, contained text, value, attribute, accessible name, and count. They poll until the assertion timeout, or the matcher's own `timeout`. `Not` inverts a matcher, which then passes after 1000 ms of continuous truth (or the whole budget when it is shorter). Text matchers take the same `TextMatch` as queries, `ignoreCase`, and a list form. The boolean flags are `visible`, `attached`, `enabled`, and `isChecked` (`checked` is a C# keyword)
- `toHaveScreenshot` as `Expect.That(Screen).ToHaveScreenshotAsync(name, options)` and the same on a locator, with `Not` and `Expect.Soft(locator)`; see [Visual comparison](#visual-comparison)
- `expect.soft` for every locator expectation, as `Expect.Soft(locator)`, including `.Not` and the per-matcher `timeout`. An `ASSERTION_FAILED` is kept and the body runs on; any other error still throws. `E2ETest` records each one on the NUnit result, as inside `Assert.EnterMultipleScope`, so the test fails when the body ends and lists every failure. `E2E.XUnit.V3.E2ETest` keeps them on the session and fails the test when it is disposed. As upstream, a failed soft assertion outranks a skip: `Assert.Ignore` or `Assert.Inconclusive` after one fails the test in NUnit, and the message keeps the skip reason beside the failures. In xUnit v3, `Assert.Skip` after one fails the test the same way. Other hosts set `E2ESessionOptions.OnSoftFailure` or call `E2ESession.CloseSoftFailures`
- `expect(browser)` as `Expect.That(Browser)`: `ToHaveURLAsync` (a string or a `Regex`, with `ignoreCase` and `timeout`), `ToHaveTitleAsync` (a `TextMatch`, with `timeout`), and `ToHaveClassAsync(locator, TextMatch)`, `.Not`, and `Expect.Soft(Browser)`. Like the locator matchers, a passing one verifies the previous `act`, and `.Not` passes after 1000 ms of the opposite. A read that outlasts the matcher's deadline ends it, so a page that stops answering fails at the assertion timeout
- `expect.poll` as `Expect.Poll(read, options)`, with `Timeout`, `Interval`, and `Message`. A read that throws is retried. The matchers are `ToBeAsync`, `ToSatisfyAsync`, and `.Not`; `E2E.NUnit` adds `ToMatchAsync` for any NUnit constraint, such as `Is.GreaterThan(3)`. The default timeout is 5 seconds, not the configured assertion timeout, because the poll does not see the running test, and it does not stop at the test deadline unless a cancellation token is passed
- `agent.act`, `agent.assert`, `agent.waitFor`, `agent.extract`. `ActOptions` has `Params`, `Timeout`, `MaxSteps`, `MaxModelCalls`, and `Agent`; `AssertOptions` has `Timeout` and `Agent`; `WaitForOptions` has `Timeout`, `Interval`, `MaxModelCalls`, and `Agent`; `ExtractOptions` has `Timeout` and `Agent`. See [Agents](#agents)
- Act tools `observe`, `scroll`, `scroll_to`, and `back`. They are offered when the engine declares `EngineCapabilities.Scroll` or `EngineCapabilities.History`. `scroll_to` with a target scrolls it into view. With text, it pages the viewport, or the target list, until a node reading the text is listed, then scrolls it into view. It stops when the screen stops moving
- Replay cache for a verified `act`: role, name, test id, and path. Modes are `self-finalized`, `agent-concluded`, and `missed`
- `Values.Unique` and `Secret`. `Values.Unique` rejects an empty or whitespace value, and a value that spells a placeholder (it contains `{{param:`). A secret value has at least 6 code points: `Secret.Create` throws `INVALID_ARGUMENT`, a config secret `INVALID_CONFIG`, and `Credentials.User` `INVALID_CONFIG` for a short `E2E_USER_*_PASSWORD`. The values of the secrets an `act` received in `Params` are redacted from every later prompt of the attempt, including the `assert`, `waitFor`, and `extract` statement and the agent's `system` and `context`. A secret filled through a locator, or read with `Secrets.Get` and never passed to `act`, is not added to that list. Redaction matches any case, JSON escapes, HTML character references, percent encoding, and collapsed inner whitespace. A known marker is never rewritten. The same secrets are redacted from the node names and test ids an `act` records as targets and end anchors in its replay cache entry, and a target, on replay or from the model, is matched against the screen in that redacted form. The same secrets are redacted from the failed matcher messages of locators and `Expect.That(Browser)`, a `toHaveScreenshot` failure, a `locator.waitFor` timeout, the soft-failure aggregate, and the messages of the inner exceptions under them. Upstream redacts error text once, at its report boundary (`serializeError`), which the port has not, so each of these places redacts its own text. The aggregate redacts when the test ends, so a secret the attempt learned after a failure was kept is covered. `expect.poll` has no session, so a poll failure redacts the secrets of every live session in the process, as upstream's `setErrorRedactor` does for the process. A cause with a secret in its message is rebuilt with the redacted text and keeps its type and code when it is an `EngineException`, `AgentException`, or `ConfigurationException`, otherwise it becomes a `TestException` with code `ERROR`, and loses its stack trace. A failed secret fill in `WebEngine` reports the Playwright message with the value and its fragments of 8 or more characters redacted. A node name cut at 256 characters, and a text or value cut at 512, that ends with the leading part of a secret (8 characters or more, or half of a shorter secret) shows that secret's marker in its place, as upstream's `redactCut` does, in the model's snapshot, the recorded targets and anchors, and the `locate` result. `StreamRedactor` and `Redactor.HoldFrom` (upstream's `SecretLedger.holdFrom`, with `maxFormLength` as `MaxFormLength`) hold back the tail of text written in pieces so a value split across two writes is still caught. The port's `Redactor` plays upstream's `SecretLedger` here (the port's own `SecretLedger` only wraps one for the MCP server), so `StreamRedactor` takes a `Redactor`, and it takes bytes as a `ReadOnlySpan<byte>`. Upstream uses them for what user code prints: a test worker's stdout and stderr, and the `e2e mcp` process's output. The port has no worker, and `e2e mcp` sends `Console.Out` to stderr as it is, so nothing in the port writes through them yet. The server's own messages are redacted whole where they are written
- `app.open`, `app.back`, `app.restart`, `app.clearState`, and `app.baseUrl` (`App.BaseUrl`), and the context `platform`. `app.restart` and `app.clearState` reopen the base URL inside their own step, as upstream's `steer`, so no `app.open` step follows them
- The `browser` fixture subset: `goto`, `reload`, `back`, `forward`, `url`, `title`, `waitForURL`, `evaluate`, `waitForResponse`, `route`, `unroute`, `unrouteAll`, `cookies`, `setCookies`, `clearCookies`, `setViewport`, `emulateMedia`, `addInitScript`, `keyboard.press`, `keyboard.type`, `keyboard.down`, `keyboard.up`, and `mouse.move`, `wheel`, `down`, `up`
- Agent budgets: `ActOptions.MaxSteps`, `ActOptions.MaxModelCalls`, and `WaitForOptions.MaxModelCalls`. A per-call budget can only lower the agent's configured one. A higher or non-positive value throws `INVALID_ARGUMENT`
- An `act` past its action budget ends `STEP_BUDGET_EXHAUSTED`, blocked. The model is told and may still conclude: a passing verdict, or a failure without a code, becomes the budget error. Replayed actions draw on the same budget. `navigate`, `back`, `scroll`, and `scroll_to` take a slot; `observe` does not. An `act` that needs one model call more than its budget also ends `STEP_BUDGET_EXHAUSTED`, blocked (`agent.act exhausted its model-call budget of N`)
- As upstream, an `act` guards against a model that repeats itself. The same call with the same input 3 times in a row, or a sequence of 2 to 4 calls twice, adds a warning. 5 identical calls, or a sequence 3 times, offers the model only `done`, so it still writes its own verdict. The `done` call never counts. The failure-streak guard is the port's own: it counts every failed action and empty turn of the act, not only the trailing run, and only asks for a verdict, without limiting the tools. An executor's transcript is kept only under `E2E_DEBUG=1`, as upstream keeps it under `--debug`.
- `ActResult.ModelCalls` (0 for a full replay) and `ActResult.Actions` (replayed and live actions, counting failed attempts)
- `AgentException.Blocked` and `AgentException.Explanation` (the same text as `Message`)
- OpenAI-compatible tool calling

## Replay cache

- A `Values.Unique` value is recorded as upstream's placeholder, `{{param:<pointer>}}` for the value as typed and `{{param:<pointer>|<encoding>}}` for another spelling (`CacheKeys.Template`, `CacheKeys.ExpandText`, `CacheKeys.ParamPointer`; `PlaceholderPrefix` is upstream's `PLACEHOLDER_PREFIX`). The port's params are a flat map, so the pointer is the RFC 6901 escaped name after one slash (`/name`, `/a~1b`); upstream's pointers also reach a value nested in the params. An entry written before this used U+0001 slots (`\u0001name|uri\u0001`); replay policy version 5 keeps those entries from being read, so the step records again. A placeholder a call cannot fill (it names a param the call did not mark, an encoding the codec does not know, or a value that encoding cannot spell, as an unpaired surrogate has no `uri` spelling) makes the entry a miss as `invalid-entry`, as upstream's `expandText` and `expandTrace` do. The port checks it once when the entry is read (`CacheKeys.TryExpandTrace`, .NET-only in its shape: upstream returns the expanded trace, the port keeps the entry as recorded to store it again and expands each text when the replay reaches it), over the typed value, the navigated URL, the scroll text, and the start and end routes. Not ported: upstream's write-side refusal of a recording whose text already spells a placeholder (`templateTrace`), and the placeholders of descriptors, summaries and upload paths, which the port does not template. An anchor's value is templated, and compared as a placeholder with the screen's own anchors projected the same way, so `TryExpandTrace` does not check it. A param key that holds `}}`, a line break, or `|` does not round-trip, as in upstream's regex and `parsePlaceholder`. Under `cache.strict`, a call whose unique value cannot be spelled in an encoding the entry uses fails as `REPLAY_STALE` with the reason `invalid-entry`. Each value is looked for in recorded text in up to five spellings, each with its own placeholder: as typed, percent-encoded as a URL path spells it (`|uri`, `encodeURIComponent`, so a space is `%20`), form-encoded as a query spells it (`|form`), as the slug an app derives for a record path (`|slug`: lowercase, letters and digits kept, every other run one dash, none at either end; a value whose slug is empty has none), and on one line (`|flat`, upstream's `flat` encoding from #1452, `TextRules.Normalize` as upstream's `normalizeText`). The `flat` slot is for a multi-line value, which the screen and the end anchors show on one line; a replay fills it with this run's value on one line, so the end check looks for it there and no longer misses. A spelling equal to one already taken is not given a slot. As upstream's `templateText` does with its literal segments, `CacheKeys.Template` never looks for a value inside a slot it wrote a moment earlier: a shorter value, such as `ull`, is not found in the slot of a longer one. `CacheKeys.Detemplate` fills every placeholder in one pass (a regex, as upstream's `expandText` is one regex pass), so a filled value is never read again. `CacheKeys.Collides` (the `param-collision` check) compares every one of those spellings across params, so a plain `"Ada Lovelace"` param next to `Values.Unique("Ada\nLovelace")` is not recorded. The port's `CacheKeys.Template` and `CacheKeys.Detemplate` do this where upstream's `templateText`, `expandText` and `ENCODERS` (`cache/template.ts`) do. Upstream's `docs/cache.mdx` line is mirrored in `skills/e2e-dotnet/references/agent.md`; the docs site has no cache guide.
- `E2E_CACHE_DIR` replaces `cache.dir` as upstream's does: it resolves from the config directory, a leading `~` or `~/` is the home directory, a blank value is ignored, and the cache mode stays as configured. Not ported: `--cache-dir` on `e2e run` and `e2e cache` (the port has no such commands), the refusal beside `cache.store` (the port rejects `cache.store`), the overlap check against `output` (the port has no `output`), and the `REPLAY_STALE` advice that names the cache directory.
- A passing locator expectation, `agent.assert`, or `agent.waitFor` after `act` verifies it, and a verified act is written. Locator reads, `locator.waitFor`, and `agent.extract` verify nothing. `agent.assert`, `waitFor`, and `extract` always run live. As upstream, verification stops when the test fails, so a check in a derived `[TearDown]` after a failure records nothing.
- Replay runs `back` and a viewport scroll as recorded, re-finds a scrolled list before each repeat, and pages again for a `scroll_to` text. Consecutive identical scrolls are recorded as one action with a repeat count. `observe` is not recorded. A recorded list scroll (and a `scroll_to` with a list) keeps the share of the viewport the list covered (`spans`, 0 to 1, from the node's box and the viewport the engine reports, as upstream's `viewportShare`). As upstream, a list that covered at least half the viewport (`MAIN_LIST_SHARE`) and cannot be re-found scrolls as the viewport does, for that repeat and every later one, and a smaller region (or a recording with no share) stops the replay. Every engine reports a viewport (`Observation.Viewport`): the web engine and the document engine as before, and `DeviceSession` and `WindowSession` the size of the screen they measure every rect against (the known viewport, and the window's size in points), so the fallback works on the mobile and Windows engines too. Upstream's mobile surface returns the same size as its observation's `viewport`; the Windows engine has no upstream. A mobile size is rounded to whole points, since `TraceViewport` is integral. The live scroll and `scroll_to` re-find a list the tree renumbered as upstream does (`resolveScrollTarget`, `samePlace`: the node itself, its descriptor, or the same-role node whose box overlaps the old one by at least half), and a lost list that covered at least `MAIN_LIST_SHARE` of the viewport scrolls as the viewport.
- When a replay ends in `end-mismatch` and the agent repairs it with more actions, the entry is evicted instead of rewritten; the next clean run records the flow again.
- The key holds the cache schema, the replay policy version, the test, the engine (its `IEngine.Name`, never its version, as upstream since `e77c17a`; the key also holds the platform), the instruction, the params, the agent's name, a SHA-256 digest of the agent's `context` with the known secrets redacted, and the repeat index. Another agent, or a changed context, records again. The repeat index counts per agent and context. Replay policy version 5 re-keys every entry, so the first run after the upgrade records them again: an entry recorded before it may hold a page load as its delta, or a unique() value as the old U+0001 slot (see the placeholder grammar below).
- A recording checks the step's delta, as upstream: up to eight nodes that appeared and up to eight that went away, alerts and status messages first, each with its value (never a secure field's), secrets redacted from names and values, and its `checked`, `expanded`, `pressed`, and `selected` states. A node counts as gone only when no node on the end screen still matches its anchor. A replay passes on its own only when the end route matches, every appeared node is present, every gone node is absent, at least one of those changes happened during the replay (counted from the first screen the replay saw on the route it ended on), and no alert shows that was not there before and that the recording never saw. The web engine does not observe Next.js App Router's route announcer (the `next-route-announcer` element), so its title echo never counts as an alert. A value the replay typed counts as a change only when the step changed nothing else. An alert's dates, times, durations, and ids are read as placeholders. A step that changed no node and stayed on its route records nothing, and an entry read for an act that then passed with nothing to record is evicted.
- As upstream, each side lists alerts and status messages first, then leaves, then containers. It skips text that reads differently on every run (ids, durations, dates, ISO 8601 instants, clock times, bare numbers, and a count that is the data rather than the step's result) while a stable anchor remains. An anchor is a visible node with a name, a text, a test id, or a placeholder, and records its role, name, text (when it differs from the name), test id, placeholder, input purpose, value, and states. A node the other fields identify is matched without its test id, so a test id that changed between renders is forgiven; a node with only a test id is matched by it. The screen a step passed on is read once it holds still. Upstream reads a recording's delta from the step's settled start screen, and measures a replay's evidence from the replay's start. The port reads both from the screen the step's first action was resolved against: a page that shows a loading state for a few hundred milliseconds after `load` holds still long enough to pass a held-still look, and a delta read from it is the page load, which a replay finds again before its own effect renders. A step that resumes a replay reads its delta from the screen the replay's first action was taken on. A node whose name or text holds a `Values.Unique` value is not an anchor.
- `ActResult.Cache` carries `ReplayedActions`, `TotalActions`, and `NotRecorded` (`param-collision`), as upstream's step cache detail does. It also carries `Detail`, as upstream's `step.cache.detail` does. On a step that read an entry it carries `RecordedBy`, the model that recorded it, as upstream's `step.cache.recordedBy` does (see [Trace page](#trace-page)). For a replay that stopped at an action it names the action as the hand-off notice does, since the port records no summary (`at action 2 of 3, tap button "Apply"`, then `: ` and the first line of the error when the action threw). After an `end-mismatch` it names the recorded nodes that did not show (`missing alert "Acme Notes"`), the ones that did not go away (`still showing ...`), the alerts the recording never saw (`unrecorded alert ...`), or that the outcome already showed before the replay acted. A store whose read throws, or that returns an entry of another schema or with no actions, is a miss with `invalid-entry`. As upstream's `step-cache.ts` does (`outcome.executed === 0`), a replay that stops before it performs any action is a miss whatever stopped it, `action-failed` and `action-uncertain` included: outside `cache.strict` the executor starts from the top with no hand-off notice, and under `cache.strict` a miss other than `gap`, `no-entry`, or an `invalid-entry` from a store whose read threw fails the step with `REPLAY_STALE` (`StepTraceSession.ReplayEntryAsync`, `FailIfStale`). Tests: `TraceReplay/ReplayThroughTheActTests` "A first action that fails is a miss, not a hand-off" and "A first action that may have committed is a miss, not a hand-off" (.NET-only: upstream has no `it` for this).
- Only the first attempt replays. A `[Retry]` attempt runs live and still records, and its acts report `missed` with reason `retry`. Each `[Repeat]` iteration is a first attempt.
- A recording that opens with `navigate` replays from any route. Any other recording needs the start route.
- A location on the app's own origin (the origin of `app.url`) is recorded and compared as its path, query, and fragment (`CacheRoute.AppLocation`, upstream's `appLocation` in `cache/route.ts`), so a recording made on one port or host replays on another, as when `app.url` uses port 0. Any other origin stays part of the route. The session applies it where upstream's host does in `observe` (`screenOf`, `agent/act.ts`), through `StepCacheOptions.AppOrigin` (.NET-only). A recording made before this holds its full origin in `route` and `endRoute`: it misses as `wrong-context` on the first run and is re-recorded. An agent `navigate` to a full URL on the app is recorded without the origin (`CacheRoute.AppNavigation`, upstream's `appNavigation`), so the step replays where the app runs then; anything else stays as given, and so does a URL with credentials or a rest that would not open the same URL. The model's link lines and the executor tree cut an app link the same way, so a path that opens with a doubled slash stays whole. .NET's `Uri` rejects a run of extra slashes after the scheme that the web's URL parser skips (`http:////host/x`), so `AppNavigation` removes them before it parses; `AppLocation` still keeps such a URL as given. A recording made before this holds the full URL in its `navigate` action: re-record it to follow the app to another origin.
- At the end of an attempt that passed, failed, or was skipped, verified acts are written and the unverified acts that recorded or replayed are evicted. An act that missed the cache and then failed leaves its key alone. A model outage or a cancelled test writes and evicts nothing, unless an assertion also failed on the app: then the unverified acts are evicted. An act is reported evicted only once the store deleted its entry (see "Recording outcome" under [Trace page](#trace-page)).
- An entry that a verified replay finished, or that already holds the same flow, is not rewritten, except to write in the step fields an older entry lacks.
- As upstream, the screen is read by one settle policy per action, for live acts and replays. After a tap, a key press, a select, a check, a navigation, or a back, the next settled look waits up to 2 s for the screen to leave the shape the action was resolved against, then reads until two looks 75 ms apart agree, for at most 1 s. After a fill it waits for the change only; after a scroll, up to 500 ms; after a secret fill, for no change. Node references, focus, and clock-like values do not count as a change, and after an action an empty document does not count as a settled screen. Upstream also counts a screenshot as the shape; the port counts the scroll position instead, so a scroll that moves no node still ends the change wait. An act's start, the screen after each action, each page of a `scroll_to` with a text, and the recording's end screen are held still; a replay settles the look before each action as the previous action's policy asks, takes a held-still look between the repeats of a scroll, and reads the end state raw.
- A replay waits up to `ReplayTimeout` (15 s; a .NET-only fixture property, not a config key) for each recorded target and for the end route. The recorded end state then gets what `Replay.VerifyEndState` (upstream's `verifyEndState`) gives it: the settling backoff (looks 100, 300, 600, 1000, then every 3000 ms apart) inside `ReplayTimeout`, then, up to the entry's `endWaitMs`, a look every second, while the step clock keeps 20 s in reserve for a hand-off. An entry records `endWaitMs` as the time from its last action (or the executor's verdict after a hand-off) to the staging read, plus a 10 s margin, at most 120 s; an entry without it waits for the backoff only. A target is still looked for every 20 ms, where upstream backs off.
- `FileStepCache.Write` is upstream's `FileCacheStore.write` (`cache/store.ts`): it writes the entry through `AtomicWrite.WriteFileAtomic`, a sibling temporary file moved over the entry file, so a crashed or concurrent writer leaves no torn entry, and two writers on one key leave the last write, as upstream's store documents. Upstream's store awaits `writeFileAtomic`; `IStepCache.Write` is synchronous, so the port uses the synchronous twin (upstream's `writeFileAtomicSync`, which its CLI and telemetry stores use). Windows-only difference: a POSIX rename replaces the target in one step, but Windows refuses a move over a file that another move is replacing (`ERROR_ACCESS_DENIED`) or that a reader holds open (`ERROR_SHARING_VIOLATION`). Upstream's `rename` does not retry, so there the losing writer throws and the recording is lost. The port retries such a move up to ten times with a growing pause (about 90 ms in all) before the error is the writer's, so the write lands and the step reports `Saved` where it would have reported `NotWritten`. A denial that lasts, such as a read-only target, reports the same error after the same wait; any other error reports at once; on other systems the retry never runs. .NET-only names: `AtomicWrite.MoveAttempts`, `AccessDenied`, `SharingViolation`, and `RetriesMove` (the Windows errors and the retry), `Utf8` (the encoding both twins write with), and `TemporaryPath` (upstream's `temporaryPath`).
- `cache.mode` `read-only` replays but never writes or evicts, including the `end-mismatch` eviction. `off` neither replays nor records. Under `cache.strict`, a stale recording fails the act with `REPLAY_STALE` and stays in place; a strict run never writes or evicts, and its retries replay. A `no-entry` miss fails too when the cache directory holds a recording of the same step under another key. Entries record the step as the test, the engine, the instruction, the params digest, the repeat index, and the agent; the port stores the engine where upstream stores the target id, and the instruction text where upstream stores its digest. Only an entry that records the whole step counts, and, outside `cache.strict`, a verified whole replay in `read-write` mode writes the missing fields into an older entry. A custom `IStepCache` is not checked. The message names what changed between the entry's `keyedBy` and this run's key context, as upstream's `keyContextChanges` does, and says "the runner, the engine, the app, or the agent's context" for an entry with no `keyedBy`.
- The entry's file name is upstream's `traceCacheKeyHash` (`cache/identity.ts`): the SHA-256 of the RFC 8785 canonical JSON of a `trace-1` key (`buildTraceCacheKey`) of the test, target, engine name and contract version, app identity, instruction digest (`instructionDigest`, normalized by `normalizeInstruction`), params digest (`paramsDigest`), repeat index (`createCallIndexer`, counted per agent name and redacted context), agent, agent context digest, and replay policy version. The port's key differs from upstream's in these parts only: `project` is the digest of the empty `projectId` (the port has no `projectId`); `appIdentity` is upstream's `targetIdentity` (`Sessions.TargetIdentity`): the digest of the target app's resolved `identity` (the declared `app.identity`, else the URL's origin and path as declared, a free port still `:0`, else the bundle id, else the build path) and `environment`; an app that declares neither keys on its URL and its host's default environment, so recordings made before `app.identity` and `environment` (which keyed on the empty declaration) miss as `no-entry` and must be re-recorded; a fixture that overrides `BaseUrl` keys on that URL; `testId` is the test title, not `<file>::<title path>`; `targetId` is the target's name and `engineName` the engine's `IEngine.Name` (the port has no engine manifest). `IEngine.Name` (upstream's `engine.name`) is a default interface member that returns `Platform`; `MobileEngine` names itself `mobile` as upstream's does, so its key and the report's `run.targets[].engine` read `mobile` where they read `ios` or `android`, and an earlier mobile recording misses as `no-entry`. The replay policy version is not bumped, as upstream did not bump it for a key change (`e77c17a` dropped the engine version from the key with a changeset only). `WebEngine` is `web`, `DocumentEngine` `document`, `WinAppEngine` `windows`; `policyVersion` is the port's own `5`: version 5 followed the placeholder grammar of `cache/template.ts`, so an entry written with the earlier U+0001 slots is never read, and its step records again. Params are projected before the digest as the port's cache has always projected them: a `Values.Unique` value is `<unique>` and a `Secret` is `<secret:name>`; a number is written by .NET's shortest round-trip form, which matches ECMAScript's for the values a param holds. The entry stores `keyedBy` (`TraceKeyContext`) as upstream does; an entry with a malformed `keyedBy` still reads, without it. **Recordings made before this key (the port's former text-hash key) are not read and are not migrated:** they miss as `no-entry` and must be re-recorded. Under `cache.strict` they do not fail as `REPLAY_STALE` either: the check matches the step by its recorded params digest, which the old entries hold in the old form, so the step runs live.

## Visual comparison

`ToHaveScreenshotAsync` compares the viewport, or one locator's box, against `<test file>-snapshots/<name>-<target>-<os>.png`, with upstream's names, OS suffixes (`darwin`, `linux`, `win32`), tolerance rules, retries until the screen matches or holds still, masks, and failure images. The pixel comparison is upstream's (the pixelmatch threshold and anti-aliasing rules) over PNGs read and written with SkiaSharp. The ported testbed PNGs are upstream's. Differences:

- A 16-bit PNG is scaled to 8 bits by Skia, which can differ from rounding by one level. Chromium writes 8-bit PNGs.
- `DocumentEngine` throws `UNSUPPORTED_CAPABILITY`. `MobileEngine` over agent-device captures the masked screenshot with `normalizeStatusBar` on, so the status bar is held fixed; the TestMu (Appium) and MAUI DevFlow clients ignore it and show the device's real status bar.
- The test file is the file the call is compiled in (`[CallerFilePath]`), not a runner's test entry. A call in a helper stores beside the helper. A build that rewrites source paths (`DeterministicSourcePaths`) breaks it.
- The update flag is `E2E_UPDATE_SNAPSHOTS=1`, or the fixture property `UpdateSnapshots`, in place of `--update-snapshots` (`-u`). There is no CLI flag or config key.
- Failure images go to `.e2e/results/<result>/attempt-<n>/` (the fixture property `ResultsDirectory` moves it). They are not attached to a step, because the port has no step report. A screenshot written earlier in the run is tracked per process, not per run directory.
- `Expect.That(screen)` is the only screen matcher. There is no `Expect.Soft(screen)`. `Expect.That(frameScreen).ToHaveScreenshotAsync` (the scope `Browser.FrameLocator` returns) fails with `INVALID_ARGUMENT`, as upstream's does, and `TreeAsync` and `DebugAsync` on it do too (`screen.tree reads the whole screen; call it on screen`).
- Secure fields are covered by the engine (Playwright masks, in every frame, including a field inside a closed shadow root, which the engine reaches through the `e2e-closed=` selector engine it registers with Playwright before it opens a browser, and again in the default context of a browser it attaches to over CDP, because Playwright seeds custom selectors only in newly created contexts; upstream's `registerCdpSelectors`) and by painting the observed secure nodes. A closed root made by declarative shadow DOM (`<template shadowrootmode="closed">`) is parsed, not attached, so the hook never sees it and the mask cannot reach it, as upstream. The record counts as present when the init script defined it on the global (`Symbol.for("e2e.closedShadowRoots") in globalThis`), not by `instanceof WeakMap`, so a page that replaces `WeakMap` keeps its closed roots tracked (upstream #1448). Upstream's cdp-recovery test `masks password fields in light and closed shadow DOM before and after reconnect` ports in full (`CdpSessionRecoveryTests.Masks_password_fields_in_light_and_closed_shadow_DOM_before_and_after_reconnect`), pixels included. Upstream's `cdp-selectors.test.ts` ports in full except one check (`CdpSelectorsTests`): the duplicate-tolerance test ports as written, against a fake message channel (`CdpSelectors.ISelectorChannel`, a .NET-only seam over Playwright's internal send, as upstream stubs `_channel`); the unsupported-context test is `Partial_` because the message names only the secure-field masks (the port's locators do not use its selector engines). Upstream counts masked regions against secure nodes before it keeps the image; the port counts them (`EngineScreenshot.MaskedRegionCount`), and a vision judgment compares them (see [Agents](#agents)).
- **Breaking, upstream #1437 (`94e6e76`): the pixel taint is gone.** A secret fill no longer turns off screenshots for the model: `Vision = On` and `Only`, an executor's `ObserveAsync(Pixels)`, the MCP `screenshot` tool, and the `e2e explore` findings keep working after a sign-in. Removed: `StepExecutorContext.PixelsTainted`, the internal `Exposure` (upstream's `SecretExposure`), `SavedSecrecy.Tainted`, and the `PIXEL_TAINTED` code, which `VisionDegradation` (`E2E` namespace) and `Vision = Only` no longer produce. `E2E.Reports.VisionDegradation.PixelTainted` stays so a report an earlier version wrote still reads, as upstream's schema keeps the value for old results. A screenshot masks secure fields only, and secret values are still redacted from all text. A generic secret in a plain input, or a value the app shows outside a secure field, is in the screenshot and reaches the model provider: use test credentials. The port has no `SECURITY.md`; upstream's change to it is covered here, in the README, and in the skill. Upstream's pixel fallback after a failed tree capture (`pixelFallback`) and the point tools are not in the port, so that part of the commit has nothing to port.
- After a secret fill, `ToHaveScreenshotAsync`, the assertion screenshots, and the failure screenshot stay on, as upstream since `58a5cec`. A model's screenshots stay on too since `94e6e76` (#1437): the port has no pixel taint, so nothing is withheld after a fill. They mask secure fields only. `ToHaveScreenshotAsync` fails with `POLICY_DENIED` and keeps no screenshot when the engine masked fewer regions than the screen lists secure nodes, or does not say (`EngineScreenshot.MaskedRegionCount` is null), as upstream's `pixelsProvenMasked` does. The failure screenshot applies the same condition, but leaves the image out of the report instead of failing.
- The name is a `string?` and the options a `ScreenshotOptions` object, so an unknown option and a non-locator mask cannot be written.
- Locator boxes inside an iframe are in the top-level viewport (past the frame's border and padding), where they used to be relative to the frame, as upstream's change for this feature does.

## Locator actions

- `locator.secondaryTap`, `longPress`, `hover`, `dragTo`, and `swipe` (`locator/screen.ts`) are `Locator.SecondaryTapAsync`, `LongPressAsync(LongPressOptions)`, `HoverAsync`, `DragToAsync(Locator)`, and `SwipeAsync(SwipeOptions)`, with the engine actions `LocatorAction.SecondaryTap`, `LongPress`, `Hover`, and `DragTo` beside the existing `Swipe`. `tap`, `doubleTap`, and `secondaryTap` take `ClickOptions { Modifiers }` (upstream's `ClickOptions`, a subclass of `ActionOptions`); the `ActionOptions` overloads of `TapAsync`, `ClickAsync`, `DoubleTapAsync`, and `DblClickAsync` stay, so existing calls compile. Modifiers on an engine without `EngineCapabilities.TapModifiers` are `UNSUPPORTED_CAPABILITY` inside the step, before the node resolves; the step label ends `with Shift`, as upstream's. `longPress` takes a whole number of milliseconds from 100 through 10000 (`ArgumentOutOfRangeException`, upstream's `INVALID_ARGUMENT`). `dragTo` resolves the drop locator inside the retry (`Locator.ResolveExactlyOneAsync`, upstream's `resolveExactlyOne`) and refuses a locator of another screen with `INVALID_LOCATOR`.
- Engines: the web engine clicks right for `secondaryTap`, clicks with a delay for `longPress` (500 ms by default, upstream's `DEFAULT_LONG_PRESS_MS`), hovers, and drags with the pointer (hover the source, press, hover the target, release; upstream uses Playwright's `dragTo` when both sides are locators). The mobile engine maps `longPress`, `hover`, and `dragTo` onto the `DeviceSession` commands that already existed and refuses `secondaryTap`. The Windows engine maps all four onto its pointer inputs. The document engine refuses all four.
- Differences: upstream's engines declare the action kinds they take and the harness refuses an undeclared one before it resolves the node. The port's engines refuse inside `PerformAsync`, so a missing node is reported first. Only the tap modifiers are checked up front (`EngineCapabilities.TapModifiers`). Upstream's refusal of an unknown option key and of `modifiers` with `position` has no port: options are typed, and the port has no tap `position` yet.
- Tests: `LocatorActionOptions/` ports `locator-action-options.test.ts` (the `modifiers` describe without its `position`, non-array, and unserializable cases; the two `longPress` `it`s; the verb theories for every verb the port has) and `ScriptedActions/` the action kinds of `scripted-actions.test.ts`. .NET-only: `PerformTests` of the mobile and Windows engines run the new actions through `PerformAsync`.

## Debug

Upstream's `--debug` prints the run's phase timings and a table of agent steps on stderr, and keeps each planned step's transcript. A test run has no `--debug` flag, so the .NET-only variable `E2E_DEBUG=1` (or `true`) stands in for it, and a fixture can override the `Debug` property. `e2e explore --debug` is the flag itself (`ExploreOptions.Debug`; the variable turns it on too). `E2ESessionOptions.Debug` carries it to the session.

- `DebugTrace` (internal, `Internal/DebugTrace.cs`) is upstream's `internal/debug.ts`: `Record`, `Time` (async, rethrows), `Summary`, and the static `Table` and `FormatMs`. It has `Off` for a caller that has no trace. It has no `Drain` and no `Merge`, because the port prints per test and has no worker channel to ship a snapshot over. `debug.test.ts` is `Debug/DebugTraceTests`.
- The phases are `session.launch` (the engine's start), `test.body` (from the start of the session until `Complete` or dispose), `session.close` (the engine's disposal), and the agent's `agent.observe`, `agent.model`, and `agent.action` (`Phases`, internal; upstream `agent/phases.ts`, where `instrumentPhase` also records step events). `agent.cache` is declared upstream and used nowhere, so the port omits it. Upstream also has `config.load`, `engine.prepare`, `engine.init`, `app.start(...)`, `collect`, and `scheduler`: the port has no such phase, because it has no runner, no app process, and no engine prepare step.
- The table is written to stderr when each session is released, once per test, where upstream prints one table for the run. The title is the same, `[e2e debug] phase timings (wall ...)`.
- The agent step table is `DebugSteps.AgentStepTable` (internal, `Report/DebugSteps.cs`), upstream's `agentStepTable` in `report/debug-steps.ts`: one row per agent step in execution order, with the step's time, the time in its model, observe, and action events, its model calls, tokens in and out, the share the provider served from its prompt cache, and its cost. A `via` column appears when the steps named several models. It is written to stderr after the phase table when each session is released, from that session's step records (upstream takes the run's results and serial groups). Differences: `StepModelInfo` has no provenance (`endpoint`, `adapterVersion`, `policyVersion`), and `IAgentModel.Name` spells provider and model together, so a step's label is that name alone unless an executor reports a provider. The `model` column sums the step's `Model` events, one per model call (`StepRecorder.AddModelCall`). The `observe` and `action` columns sum the step's `Observation` and `Engine` events (see [Trace page](#trace-page)). `cached` and `cost` read `-` unless the provider or an executor reports them in `ExecutorModelCall`. Every built-in provider returns the cache read tokens (and the write tokens, where it has them) in `ModelCallUsage`, and `ToolLoop` and the agent's own loop (`Agent.cs`) pass them on. The AI trace still writes only the input and output tokens. Bedrock and Anthropic report the cached tokens apart from the input tokens, so the port adds them back into `InputTokens`, as the AI SDK does (`convertAmazonBedrockUsage`: `total: inputTokens + cacheReadTokens + cacheWriteTokens`), and upstream's `ModelUsage.record` reads that total. Google counts the cached tokens inside `promptTokenCount` already. The OpenRouter cost is the field upstream's `readCost` reads (`metadata?.['openrouter']?.['usage']`, then `cost`). A count that is negative or not whole is dropped, as upstream's `tokenCount` does. Only an OpenAI-compatible endpoint reports a cost, and only when it sends `usage.cost`, as OpenRouter does. Upstream's `readCost` also reads the AI Gateway metadata; the port has no gateway. `debug-steps.test.ts` is `DebugSteps/AgentStepTableTests` (both `it`; the first is partial: the port has no serial groups, so its third step is a second attempt's). `.NET-only`: `ModelCallUsage` (the per-call usage a model returns, in `ModelResponse.Usage`; upstream reads the AI SDK's usage object; a breaking rename of the port's former public `ModelUsage`, whose name is now upstream's accumulator, see [Model usage](#model-usage)), the agent step table case of `SessionDebugTests`, `ModelCallUsageTests` and `Provider_usage_carries_the_cache_split_and_the_cost_when_reported`.
- An executor's `AttachTranscript` text is kept as `transcript-<n>.txt` only under debug. `.NET-only`: `SessionDebugTests`, and the debug-on and debug-off cases of `AttachedTranscriptTests`.

## AI trace

Upstream's `--ai-trace` writes every model call of the run to `<output>/ai-trace.json`, in the AI SDK devtools shape (`{ runs[], steps[] }`) that `npx unbox-ai` reads. One run is one agent step, and one step is one model round trip. A test run has no `--ai-trace` flag, so the .NET-only variable `E2E_AI_TRACE=1` (or `true`) stands in for it, a fixture can override the `AiTrace` property, `e2e explore --ai-trace` is the flag itself (`ExploreOptions.AiTrace`; the variable turns it on too), and `E2ESessionOptions.AiTrace` carries it to the session.

- `AiTraceRecorder`, `AiTraceCollector`, `AiTraceScope`, `AiTraceRun`, `AiTraceStep`, `AiTraceDocument`, `withAiTraceScope` and `withAiTraceStep` (as `AiTraceScopes.WithAiTraceScope` and `WithAiTraceStep`), and `stringify` (as `AiTrace.Stringify`) are upstream's `internal/ai-trace.ts` (all internal, `Internal/AiTrace.cs`). The recorder keeps upstream's rules: a run per step, a nested run per tool, steps numbered without collisions, the prompt as sent with the system prompt in front, and inline media replaced by `[binary N bytes omitted]`. Its `drain` is `Drain(all)`.
- Upstream's recorder is an AI SDK telemetry integration, so `registerAiTraceRecorder` and `dispose`'s removal from the SDK's list have no port. The recorder's `onStart`, `onStepStart`, `onLanguageModelCallStart`, `onLanguageModelCallEnd`, `onStepEnd`, `onEnd`, `onError`, and `executeTool` are methods (`OnStart`, ...), and `AiTraceModel.CompleteAsync` (.NET-only, `Agent/AiTraceModel.cs`) fires them around each model call. Both places that ask a model for a turn, the tool loop and the judgment path, go through it, so a custom executor with a model of its own is traced too. A custom executor that calls a provider directly is not seen. Upstream's AI SDK keeps a generation open while its tools run, so a generation a tool starts is a child of the step that called it. The tool loop does the same: `AiTraceModel.BeginAsync` leaves the step and the generation open, the loop runs every tool of the turn through `ExecuteTool` (via the .NET-only `AiTraceTurn.ExecuteToolAsync`), and the step ends (`OnStepEnd`, `OnEnd`) after the tools ran. A path that has no tools (the judgment path) still ends the generation as soon as the model answers. No tool of the port starts a model call today, so the link only shows when a custom tool does.
- The scope comes from `StepRecorder`, as upstream's `steps.ts` does: each step enters the attempt's scope and narrows it to its api and label. The attempt's scope is built by the session (the test title is also its `TestId`). The port has no worker, so there is no `drain` over a channel: the session drains its recorder when it is released, the process adds it to one `AiTraceCollector` per file, and it rewrites the file at most every 2 seconds and when it exits.
- The file is `ai-trace-<process id>.json` next to the results directory (`.e2e/` by default), not `ai-trace.json`. A test run can use several processes (one per test project), and each rewrites only its own file. Open it with `npx unbox-ai <file>`.
- What the model sees is redacted by the same redactor as the request, and the trace redacts it again on the way in: text, tool arguments, the response, and a failure message. Screenshots are byte counts. The port's `ModelCallUsage` has the cache read and write tokens but no `inputTokenDetails` object, so `usage` has no `inputTokenDetails`, and `output` has no `providerMetadata`. The response has no `id`. `provider` is the model class without `Model`, such as `Anthropic`.
- Tests: `ai-trace.test.ts` is `AiTrace/` (13 of 14; "registers through the SDK loader and tolerates a missing SDK" is skipped, since there is no SDK; "records the status and the body of a provider error the SDK could not parse" goes through `OpenAiCompatibleModel` and expects the port's `The model provider failed: HTTP 400: ...` message). `ai-trace-media.test.ts` is `AiTraceMedia/` (3 of 3). `agent-ai-trace.test.ts` is `AgentAiTrace/` (2 of 3, partial: the model is the port's `ScriptedModel`, so the model id is `scripted` and the provider `Scripted`, and there is no run outcome, so the test reads the file; "--ai-trace on child-process workers" is skipped, since the port has no workers). `.NET-only`: `AiTraceModelTests` (redaction, screenshots, concurrent tests).

## Mobile snapshot model

`E2E.Mobile` ports the pure logic of `@e2e-dev/mobile`: the projection of an agent-device accessibility snapshot onto `SemanticNode` (`SnapshotProjection`), locator expressions and agent-device selectors over it (`DeviceLocator`, `AgentDeviceSelector`), error translation (`DeviceErrors`), links, screenshot masking, and the shared helpers (`DeviceSupport`). The client, pool, provider, and engine are in [Mobile engine](#mobile-engine). Differences:

- agent-device is a Node package. `AgentDeviceError` stands in for its `AppError`, and `AgentDeviceSelector` reads the selector grammar of `parseSelectorChain` and applies the term rules of `listSelectorChainMatches` to the raw nodes, for the target's platform (the keys `id`, `role`, `text`, `label`, `value`, `appname`, `windowtitle`, and the flags `visible`, `hidden`, `editable`, `selected`, `focused`, `enabled`, `hittable`).
- An `AMBIGUOUS_MATCH` failure (several devices match and no selector narrows it) keeps agent-device's message, code, details, and hint, and `DeviceErrors` adds one sentence to the text: `Set MobileOptions.Device to a device id, or boot exactly one device.` Upstream adds nothing. `AmbiguousMatchTests` covers it and has no upstream counterpart.
- `SemanticNode.States` holds plain booleans, so it cannot tell an unchecked switch from a node with no checked state. `ProjectedNode.States` keeps the states the platform reported, and `ProjectedNode.Selector` keeps the `id=` hint upstream puts on the node.
- A `filter` with `hasText` honors the exactness of its text pattern, as upstream's `matchesText` does. `Locator.Filter(TextMatch)` is a substring match (upstream's `toTextPattern(hasText, { exact: false })`), so a locator test sees no difference. `TextMatch` holds no exactness, so the expression carries it: `LocatorExpression.HasTextExact` (.NET-only; default `false`) makes `HasText` equal the text, as upstream's `exact('About')` does in `locate.test.ts`. `HasNotTextExact` is the same for `HasNotText`. A `Regex` ignores it. The core resolver (`Screen`) reads it too.
- A role query has no `hidden` state. Role queries skip hidden nodes, as upstream's do.
- Link parsing reads a URL with `System.Uri`, after the whitespace rules a browser applies.
- `MaskPng` refuses a PNG with no end chunk, as upstream's parser does.

## Mobile engine

`MobileEngine` ports `engine.ts`, `options.ts`, `bindings.ts`, `pool.ts`, `provider.ts`, `surface.ts`, `actions.ts`, `device.ts`, and `tools.ts`. It implements `IEngine` and declares every capability, video included. `DeviceSession` is the surface, `DeviceActions` (the `IDeviceActions` the engine uses by default) turns a node and an action into commands, `Device` is the `device` fixture, and `MobileTools` is the agent tool pack. The `eas` and `limrun` providers are ported (see [EAS Simulators](#eas-simulators) and [Limrun](#limrun)); a provider's own recording (`DeviceProvider.record`) is `IDeviceProvider.RecordAsync` (see [Provider recording](#provider-recording)). Differences:

- agent-device is a Node program. `IDeviceClient` stands in for upstream's `createAgentDeviceClient`: a call is `namespace.method` with an options object, as upstream's client names them. `AgentDeviceRpcClient` implements it over the daemon's HTTP JSON-RPC 2.0 (`POST /rpc`, method `agent_device.command`, `GET /health`). The wire format was read from agent-device 0.21.22's code and checked against a running 0.21.22 daemon for `devices`, `boot`, `close`, `session_list`, `prepare`, and `snapshot`. A running 0.21.25 daemon was checked for `GET /health` (protocol 2) and `session_list`. A running 0.21.29 daemon answered `GET /health` (protocol 2, version 0.21.29), `session_list`, and `devices` in the same envelope, and its `daemon.json` still carries `httpPort`, `token`, and `version` (it adds `capabilities` and `plugins`, which the client ignores). The 0.21.26 to 0.21.29 release notes list no change to the RPC envelope or to the commands the engine sends; the changes that touch the engine are in its commands (a coordinate `fill` that names no text input is refused on iOS, a `find` focus match behind the visible keyboard is refused, an alert `dismiss` picks a listed decline, and a delayed launch confirmation is surfaced), and none of them was exercised on a device. The 0.21.30 to 0.21.35 release notes likewise list no change to the RPC envelope or to the commands the engine sends (they add gesture and hardware-button commands the engine does not use, a typed reason on `apps` and `logs` refusals, a 404 for an expired resource id, and iOS and Android snapshot and fill fixes, an unscoped `boot` that picks the newest of several shut-down devices, and an iOS return press with nothing focused that keeps the runner session); no 0.21.35 daemon was reached, because a daemon does not start on this Windows host (0.21.29 fails the same way). It is not a documented protocol, so the version is pinned (`AgentDeviceVersion.Pinned`) and the client checks `rpcProtocolVersion` and the daemon version. `DeviceCommands` turns each call into a command, positionals, and flags. The calls the engine makes today are covered. A call it does not know is refused.
- A local daemon needs Node 22.12 or newer. The first call starts it the way agent-device's own CLI does (`npx --yes agent-device@0.21.35 session list --json`, with `AGENT_DEVICE_DAEMON_TRANSPORT=http`), in the state directory `~/.agent-device/e2e-dotnet`, and it keeps running after the command. `E2E_AGENT_DEVICE_BIN` names an `agent-device.mjs` to run in place of `npx`. A missing Node, a Node that is too old, an agent-device that does not start, and a daemon of another version fail with `INVALID_CONFIG` and the recovery. Starting a daemon on Windows is not verified.
- `MobileOptions` carries the app (`App`: bundle id, build path, launch arguments, permissions), the target name, and the device choice as three properties (`Device`, `Devices`, `Provider`; at most one), because the port has no target config for a device yet. Permission names and states are enums, so an unknown one cannot be written. `Settle` and `SettleMilliseconds` stand in for `settle: number | false`.
- The core engine contract has no `prepare`, `finish`, `init`, or worker slot. `MobileEngine.PrepareAsync` and `FinishAsync` take their own info records, and `StartAsync(MobileStartInfo)` starts the worker of one slot. `StartAsync(EngineStartOptions)` starts slot 0 of the target. Bindings travel from prepare to a worker through `MobilePrepareResult.Env`, as upstream's environment variable does. In one process the pool also keeps them.
- `app.open()` is `OpenAsync`: it launches the pinned app fresh. A deep link or any absolute URL is refused. `EngineStartOptions.BaseUrl` is refused as upstream refuses `app.url`.
- `DeviceSession.BackAsync` always settles (upstream's agent origin), since a test step has no origin here.
- The core session has no attempt hooks, pixel observations, or artifact directory. So `DeviceSession` is one attempt (it registers on the engine until it closes), and `ScreenshotAsync` returns the masked, status-bar-normalized PNG for `toHaveScreenshot` instead of writing numbered files. A secure field that cannot be masked still withholds the image with `ENGINE_FAILURE`.
- `DeviceSession.LocateAsync(LocatorExpression, TimeSpan timeout, CancellationToken)` is upstream's `locate` (`surface.ts`), so a locator or `Expect` on a device resolves in the engine. It snapshots with `interactiveOnly: false`, runs `DeviceLocator.ResolveExpression`, and binds the matches in a separate map capped at 2048 (the oldest goes first; an older ref is `NODE_STALE`). It hands the capture it matched against to `EngineStartOptions.Screen`, and tells `EngineStartOptions.Environment` the platform and device once, when the session starts. Differences: `timeout` is the budget left (upstream's `operation.timeoutMs`), since the core session has no operation context; the expression is one flat record (`LocatorExpression`) where upstream's is a union of `query`, `filter`, `index`, `union`, `selector`, and `frame`; and the port's refs carry no revision, so upstream's `rejectSupersededLocate` has no port (a device mints a new id for every projection, so a later locate never reuses a ref). Core retries a retryable `EngineException` of a locate until the wait's deadline, as `resolveOnce` does.
- Upstream's Android locate (`fix(mobile): keep locator polling through unreadable android snapshots`, `4fe6baf`) is ported. - The sample (`samples/MobileApp.E2ETests`) derives from `MobileAppTest` (see [MobileAppTest](#mobileapptest-not-in-upstream)). ## EAS Simulators

`EasSimulators` (the `E2E.Eas` package, namespace `E2E.Eas`) ports `@e2e-dev/eas`: hosted iOS simulators and Android emulators from Expo, leased through Expo's GraphQL API over `HttpClient`, with no SDK. The provider is its own package, `E2E.Eas`, which depends on `E2E.Mobile`, as upstream's `@e2e-dev/eas` is a package of its own. It keeps a private copy of the shared `HttpClient`, so `E2E.Mobile` exposes nothing extra for it. Pass it as `MobileOptions.Provider`. The sessions, the queue and startup limits, the idle backstop, the `EXPO_TOKEN` or eas-cli login, and the project id from the app config follow upstream. Differences:

- Options are the `EasSimulatorsOptions` record, so an unknown option key is a compile error and upstream's `rejectUnknownKeys` has no counterpart. A bad combination (`BuildId` with `ApplicationArchiveUrl`, an idle limit not below the duration) is `INVALID_CONFIG` from the constructor.

## Limrun

`LimrunSimulators` (the `E2E.Limrun` package, namespace `E2E.Limrun`) ports `@e2e-dev/limrun`: one hosted iOS simulator or Android emulator per worker slot, created, polled to ready, driven through an agent-device daemon the provider starts for it, and deleted on release. Pass it as `MobileOptions.Provider`. The key and base URL (`LIMRUN_API_KEY`, `LIMRUN_BASE_URL`), the instance spec, the daemon environment, the retained lease, the 20-second heartbeat, and the cleanup follow upstream. The client has the lease commands the provider needs: `leases.allocate`, `leases.heartbeat`, and `leases.release` (`DeviceMethods`), sent as agent-device's `agent_device.lease.*` JSON-RPC methods. Differences:

- The provider is its own package, `E2E.Limrun`, which depends on `E2E.Mobile`. Upstream's `@e2e-dev/limrun` is a package of its own too. The package keeps private copies of two small `E2E.Mobile` internals (the argument builder and the shared `HttpClient`), so `E2E.Mobile` exposes nothing extra for it.
- Limrun's REST API (`/v1/ios_instances` and `/v1/android_instances`: create, get, delete) is called over `HttpClient`, with no `@limrun/api` SDK. Like upstream's configuration of the SDK, it retries nothing and gives each request 60 seconds.
- Upstream forks a Node process per device, so the daemon and its lease client get the instance's credentials without changing the runner's environment. The port starts the daemon itself, with exactly the run's environment plus the instance's (`AgentDeviceDaemon.LocalAsync` with an environment), and runs the lease and install calls in the runner. `AgentDeviceDaemon.StopAsync` runs `agent-device daemon stop --clean`.
- Upstream pins agent-device as a dependency of `@e2e-dev/limrun`, at the engine's version (0.21.35), and checks that the installed one matches. The port always starts the pinned release (`AgentDeviceVersion.Pinned`), so nothing is installed by hand. It only checks that the engine asked for that release, and the daemon's own version check runs when it starts.
- The lease request leaves out `providerCredentialFingerprint`. The daemon only compares it with the credentials of a daemon that was already running, and the port starts a fresh daemon with the right credentials for every device.
- Options are the `LimrunSimulatorsOptions` record, with enums for the device models, so an unknown option is a compile error and upstream's `rejectUnknownKeys` has no counterpart.
- Upstream's Limrun page (`docs/integrations/limrun.mdx`) is ported as `docs-site/src/content/docs/integrations/limrun.mdx`, with the port's C# names. Its `examples/with-limrun` app-flow example is not ported: `samples/MobileApp` is the port's mobile example.
- Not verified against a live service: the lease wire format was read from agent-device's code (the `agent_device.lease.*` methods and their params in the daemon, and the client that writes them), and Limrun's REST calls from the `@limrun/api` 0.59.0 source. No test reaches Limrun or a daemon.

## In-flight commands

agent-device takes no abort signal, so a command a cancel or a timeout abandoned keeps running on the device. Upstream's surface keeps them in `inflight` (`track`, `settleInflight`) and its `startAttempt` waits for them before it opens anything, so a ghost tap never lands in a retry. The port has the same behavior:

- `DeviceSession.Track` is upstream's `track`: `CommandAsync`, `ActAsync` (upstream's `perform` registration), and every `InputBudget` register the device command until it settles. `DeviceSession.SettleInflightAsync` is `settleInflight`, and `DeviceSession.StartAsync` calls it first, with the caller's token, as `startAttempt` does: a command that never settles fails the start as `CANCELLED` once the token ends, and the boot never goes out.
- Differences: upstream's surface is the worker, so it holds the set. The port's session is one attempt, so `MobileEngine.InflightOf(target, slot)` holds the set of a worker slot (`InflightCommands`, .NET-only) across the attempts that drive it. A command that fails after its caller left is read once and never reported. The set is keyed by target, slot, and the lease or device the binding names, so an engine reused for another run does not wait on a released device's commands. The wait is also bounded by `E2EDefaults.LaunchTimeout` when the caller's token never ends (`ENGINE_FAILURE`). Upstream's client takes no abort signal, so an abandoned command is still running when it is tracked. The port's HTTP client would abort its request on a cancel and end the tracked task while the daemon may still run the command, so `DeviceSession.Client` is a `TrackedClient` (.NET-only): it calls `IDeviceClient.CallAsync` with a token the caller cannot cancel, tracks that call itself, and the caller leaves by racing it, so a cancel still surfaces as `CANCELLED` at once. Once the caller has left, the request has `E2EDefaults.LaunchTimeout` to answer (the bound of the next start's wait) and is aborted after that. An aborted request that ends without a successful answer leaves daemon completion unconfirmed: `InflightCommands` blocks later attempts for that target, slot, and device with a non-retryable `ENGINE_FAILURE` for the lifetime of that engine. A request that fails after the caller left counts as unconfirmed unless the failure is an error the daemon itself reported (`AgentDeviceError.Reported`, .NET-only); a transport or client-side failure is unconfirmed. A client that ignores the abort and successfully answers still confirms completion. The DevFlow client sequences its own steps and implements the .NET-only `ICancellableDeviceClient` and is not detached (Appium keeps its tracked, detached path), so a cancel stops its following steps, such as the lease claim after the DevFlow status read. `TrackedClient` accepts a .NET-only `TimeProvider` for testing this deadline. A command that is not cancelled is not bounded, as before. Test: `Engine/SessionHooksViewportSwipeLocationArtifactsTests`, 'Keeps_a_cancelled_command_in_flight_until_the_daemon_answers_even_when_the_client_honours_its_token' (.NET-only), and `Engine/TrackedClientTests`, 'Blocks_later_attempts_after_an_abort_without_daemon_confirmation' and 'Allows_the_next_attempt_when_a_client_ignores_the_abort_and_confirms_completion' (.NET-only). Closing a session (upstream's `endAttempt` or `dispose`) does not settle the in-flight commands.
- Tests: `Engine/ObservationTests`, 'keeps a timed-out input in flight: the next attempt waits for the device command to settle', and `Engine/SessionHooksViewportSwipeLocationArtifactsTests`, 'waits for an abandoned command to settle before the next attempt starts and its launch goes out'. Both wait on a command the test releases, not on a timer, apart from the 200 ms input budget of the first.

## Provider recording

`IDeviceProvider.RecordAsync(lease, context, ct)` is upstream's `DeviceProvider.record`. When an attempt records video and the slot rides a provider's lease, `DeviceSession.StartVideoAsync` calls it in place of agent-device's recording, with the lease as it traveled to the worker (`DeviceProviders.TravelledLease`, upstream's `travelledLease`: the id and the declared fields, never what a derived lease class kept) and a `ProviderRecordContext` of `RunId`, `TargetName`, `AttemptId`, and `Env`. `DeviceProviders.RecordLeaseAsync` is `recordLease`: a failure is `ENGINE_FAILURE` naming the provider and the lease, a failure met once the token was cancelled is `CANCELLED`, and a token already cancelled never reaches the provider. `StopVideoAsync` ends the recording with `ProviderRecordings.StopProviderRecordingAsync` (upstream's `stopProviderRecording`) into a `VideoFile` or a `VideoLink`; the recording is marked at once and cleared when the provider confirmed the stop, before what it wrote is checked; a stop shared by concurrent callers runs once. Closing the session stops a recording still marked, best effort. `DevicePool.Recorder` is `pool.recorder`, and `LeasedDevices.Recorder` is `recorder`. Differences:

- Upstream's `record` is optional, and a provider without one records with agent-device. A C# interface member has no absence to test, so the default `RecordAsync` returns null and a provider that returns null records with agent-device, as `IBrowserProvider.RecordAsync` does. `LeasedDevices.Recorder` is always the provider. Upstream's `asDeviceProvider` check that `record` is a function and `isProviderRecording`'s check for a `startedAt` and a `stop` have no port: the types say it. The context's `signal` is the `CancellationToken` parameter.
- `MobileStartInfo.AttemptId` (upstream's `EngineAttemptContext.attemptId`) names the recording's attempt. `EngineStartOptions.AttemptId` fills it, and a new id is made when it is absent. A run through the test host sets no `RunId` yet, so `ProviderRecordContext.RunId` is empty there.
- Upstream's worker outlives its attempts and keeps what an attempt could not stop: a provider recording whose stop failed is retried at the next `startAttempt` (which then blocks), a native recording that could not be confirmed stopped resets the leased session before the next attempt, and a worker disposed while the lease is reused keeps its session. The port's session is one attempt that always ends its agent-device session: a recording whose stop failed is retried once, when the session closes, and then abandoned, and nothing is retained for the next attempt. Providers must clean up their recordings when they release a lease.
- Tests: `Provider/DeviceProviderRecordingTests` ports 10 of the 22 `it` of `describe('device provider recording')`. Eight follow upstream: 'records through the provider instead of agent-device, from the worker, with the lease id and the declared lease fields', 'reports a recording the service keeps as a link', 'keeps the agent-device recording for a provider without record', 'keeps the agent-device recording for a worker without a lease, when no prepare ran', 'names the provider and the lease when record fails, and has nothing to stop at attempt end', 'cancels a start whose budget ran out, and stops the recording that came up anyway at attempt end', 'never asks the provider to record for an operation already cancelled', and 'keeps a recording whose stop failed, so endAttempt stops it once more'. Two are partial (`Partial_` prefix): 'stops a provider recording without closing its leased session when the worker is disposed mid-attempt' (the port closes the session, so it checks the stop only) and 'clears a confirmed provider stop before rejecting its invalid artifact' (it checks the stops, not the reuse of the session). Skipped: 'refuses a provider whose record is not a function' (the type says it), and 11 that need a worker that survives attempts and retains a recording or its session: 'keeps a reusable leased session when the provider recording still cannot stop during disposal', 'finishes a retained provider recording before the next attempt records in the same worker', 'blocks the next attempt while its retained provider recording cannot stop and preserves its owner', 'does not begin another attempt or record when a retained provider stop wait is cancelled', 'resets a leased session whose native recording still cannot stop after endAttempt', 'resets an unconfirmed native recording before another attempt in the same worker', 'fails the next attempt when its native recording reset cannot close the session', 'keeps an unconfirmed native recording after its stop wait was cancelled', 'preserves a session after native stop succeeded even when moving its artifact fails', 'retries an unconfirmed provider stop after endAttempt during disposal', and 'shares a pending provider stop and closes on reuse revocation before the stop resolves'. .NET-only: 'keeps the agent-device recording for a provider that records nothing of this device' (a provider whose `RecordAsync` returns null).

## Kernel

`KernelProvider` (the `E2E.Kernel` package, namespace `E2E.Kernel`) ports `@e2e-dev/kernel` at the port's parity commit: `kernel()` from `provider.ts`, the Kernel client from `client.ts` (`KernelBrowsers`, `kernelBrowsers`, `KernelBrowserParams`, `KernelReplayParams`), and `envValue` from `env.ts`. It is a `WebEngineOptions.Browser` provider: `Name` is `kernel`, `AcquireAsync` creates a browser, `ReleaseAsync` deletes it, `SweepAsync` deletes the run's active browsers, `Downloads` reads a download back through the browser filesystem, and `RecordAsync` records a Kernel replay. Lease tags, the 600 s idle timeout, the cancelled-request delete, the sweep message, and the `replay.mp4` replay with its retried download follow upstream. Differences:

- Upstream's function `kernel(options)` is the class `KernelProvider` (a type named `Kernel` would clash with the namespace). `KernelOptions` is a record that extends `KernelBrowserParams`, as upstream's interface does.
- There is no Kernel .NET SDK (no package from Kernel on NuGet; Kernel publishes Node, Python, and Go SDKs). The client calls Kernel's REST API with `HttpClient`, the API key as a bearer token, and replaces `@onkernel/sdk`: `POST /browsers`, `DELETE /browsers/{id}` (404 counts as deleted), `GET /browsers?status=active&tags[k]=v` (paged by `X-Has-More` and `X-Next-Offset`), `POST /browsers/{id}/replays`, `POST .../replays/{replayId}/stop`, `GET .../replays/{replayId}` (`Accept: video/mp4`), and `GET /browsers/{id}/fs/read_file?path=`. The base URL is `https://api.onkernel.com/`, or `KERNEL_BASE_URL` from the run's environment (the SDK reads it from the process environment). The SDK retries a failed request twice; the client retries nothing, since a retried create could allocate a second browser. The SDK keeps one client per API key; the client here is stateless, so the provider builds one for each request. An error answer becomes a `KernelApiException` with the SDK's message, trimmed (`401 Invalid or disabled API key`).
- Upstream types the create-browser body as the SDK's `BrowserCreateParams`. `KernelBrowserParams` has properties for `stealth`, `headless`, `gpu`, `timeout_seconds`, `profile`, `proxy_id`, `viewport`, and `tags` (`Stealth`, `Headless`, `Gpu`, `TimeoutSeconds`, `Profile`, `ProxyId`, `Viewport`, `Tags`), and `Extra`, a JSON object for any other field by its wire name (`proxy`, `extensions`, `region`, ...), which the properties win over, so the run's tags and timeout stay. Upstream's `replay` is a boolean or the start-replay body; the port has `Replay` (default true) and `ReplayParams`. `Scope` is `null` for the default, `BrowserProviderScope.Worker`.
- The web engine calls `RecordAsync` for an attempt that records video (see [Video](#video)): the replay is the attempt's `video/replay.mp4`, and a headless browser, or `Replay = false`, gets the engine's screencast. A download the browser took (`Browser.WaitForDownloadAsync`, see below) is read from the provider's `Downloads` when the lease serves them (`Downloads.SaveDownloadsToAsync`, tested in `ProviderDownloads/`). The provider tests both against a fake Kernel; the recording is not checked against a live Kernel.
- Not verified against a live Kernel, because no `KERNEL_API_KEY` was available. The endpoints, field names, and paging headers were read from the `@onkernel/sdk` 0.113.0 source (`browsers.ts`, `replays.ts`, `fs.ts`, `core/pagination.ts`, `client.ts`), the version upstream pins. The wire format may differ from what is written here; a first run against a real account is the check.
- `tests/E2E.Kernel.Tests` ports `packages/kernel/tests/unit/kernel.test.ts`: `Kernel/KernelTests.cs` for `describe('kernel()')` and `Kernel/KernelRecordTests.cs` for `describe('record')`, 15 of the 16 `it`. The 16th, "keeps the idle timeout backstop for an undefined option from a JavaScript config", has no C# counterpart: an unset `TimeoutSeconds` is `null`, and "creates a browser with the run tags and the idle timeout backstop" checks it. Two have the suffix `PARTIAL_` in the name: "fails without an API key in the run environment and reuses one SDK client per key" (no SDK client to reuse; the test checks that each request carries the key of its run) and "records a Kernel replay of the browser ..." (a call has no signal of its own to compare with the step's). The mocked-SDK harness is `FakeKernel`, a fake `HttpMessageHandler`. `RestApi/KernelRestApiTests.cs` has six .NET-only tests of the REST requests (base URL, create body fields, a JSON error body, paging), which no upstream `it` covers.

## TestMu mobile

`E2E.TestMu.Mobile` drives TestMu AI real and virtual mobile devices through Appium. Upstream has `@e2e-dev/testmu` (commit `88ed717`), a `testmu()` device provider that leases a device for each worker slot and drives it through an agent-device daemon (`daemon.ts`, `driver.ts`, `heartbeat.ts`, `sessions.ts`). The port does not port it. It talks to TestMu's hub with Appium instead, so every type here is .NET-only. The package depends on `E2E.Mobile` and holds an `IDeviceClient` over a W3C WebDriver session on TestMu's hub (`https://mobile-hub.lambdatest.com/wd/hub`), with the flat `LT:Options` capabilities TestMu documents. It is a preview: no provider leases a device yet, and the page source is not converted to a snapshot yet, so `capture.snapshot` fails with `NOT_IMPLEMENTED` (`UNSUPPORTED_CAPABILITY` in a test). What it does:

- `E2E.Mobile` gets one new public interface, `IDeviceClientSource`, which has no upstream counterpart. A `MobileOptions.Provider` that implements it makes the `IDeviceClient` for each session, in place of the agent-device client. A worker in another process builds its engine from the same options, so its provider object makes the client there. What the client needs to find the leased device travels in `DeviceLease.Client`, which reaches the worker as `DeviceConnection.Client`. Any other provider is unchanged.
- Supported: launch and terminate an app, deep links, tap, double tap, long press, fill, type, swipe, pan, drag, scroll, screenshot, home, back, native alerts, the keyboard (Enter and dismiss), orientation (portrait and landscape), and the clipboard. A `ref` finds the node's rect in the newest snapshot, and a tap lands on its centre. A ref of an older snapshot is stale (`NODE_STALE`).
- Refused as `UNSUPPORTED_OPERATION`, which a test sees as `UNSUPPORTED_CAPABILITY`: permissions, appearance, biometrics, location, wifi and airplane mode, clearing app state, the keychain, hover, folding, the foreground app, installing a build from a test, and launch arguments except on an iOS relaunch. The provider will install the app when it leases the device.
- `sessions.close` does nothing. The engine closes at the end of every attempt, and the next attempt drives the same device, so only the provider's release will end the session.
- `fill` taps the field and writes to the focused element, because a snapshot ref is not an Appium element id. `back` on iOS taps the first button in the navigation bar, as agent-device does, and fails when the screen has none; Android uses the system back.
- `settle` options are ignored: the engine settles on observe. `normalizeStatusBar` is sent on for the masked screenshot an observation takes, but the Appium client ignores it (Appium cannot normalize the status bar), so a screenshot shows the device's real status bar.
- The package is in CI's pack step but not in the release workflow until the provider lands. Not verified against a live account: every wire detail was read from TestMu's and Appium's documentation, and the `mobile:` script names and arguments were not sent to a real hub. The unit tests use a fake hub. Among them: whether the hub accepts the `LT:Options`-only capabilities without a top-level `platformName`, the session id field, and which `mobile:` commands it forwards.

### What still differs from upstream's `@e2e-dev/testmu`

`E2E.TestMu.Mobile` serves the same TestMu AI devices another way, so it is a client, not a port. Compared with upstream's device provider (`provider.ts`, `daemon.ts`, `driver.ts`, `heartbeat.ts`, `sessions.ts`):

- No `IDeviceProvider` leases a device: upstream's `testmu(options)` (`device`, `osVersion`, `app`, `deviceType`, `project`, `build`, `sessionName`, `orientation`, `geoLocation`, `timezone`, `language`, `locale`, `appiumVersion`) has no counterpart. Nothing uploads the build from `app`, names the dashboard session (`e2e-<run id>-<target>-<slot>`, with the project and the build), or releases the session at the end of a run. The package opens its session from a `TestMuSessionRequest` a caller builds.
- No `RecordAsync`: upstream's `record` finds the lease's session on the dashboard (`findSession`) and returns its video URL (`sessionVideoUrl`) as a `video/mp4` link, with the session's start time. The seam is ported (see [Provider recording](#provider-recording)), and nothing on TestMu's side feeds it. The client refuses `recording.record`, so a TestMu device has no video.
- No agent-device daemon or plugin: upstream starts one daemon per slot with `@agent-device/testmu`, checks its version (`assertDriverVersion`), keeps the lease alive with a heartbeat (`LEASE_TTL_MS`), and allocates with `retainOnClose`. The port has no heartbeat.
- The page source is not converted to a snapshot, so a test cannot observe the screen (`capture.snapshot` is `NOT_IMPLEMENTED`).
- Credentials: upstream reads `LT_USERNAME` and `LT_ACCESS_KEY` from the run's environment (`testmuCredentials`); this package takes the hub credentials from its request.

## MAUI DevFlow (not in upstream)

`E2E.Mobile.DevFlow` drives a .NET MAUI app through the [MAUI DevFlow](https://github.com/dotnet/maui-labs/tree/main/src/DevFlow) agent, the HTTP server `Microsoft.Maui.DevFlow.Agent` runs inside the app in Debug builds (`builder.AddMauiDevFlowAgent()`). Upstream has no counterpart, so every type here is .NET-only. The package depends on `E2E.Mobile` and holds an `IDeviceClient` over the agent's `/api/v1` API plus the provider, `DevFlowAgents`, an `IDeviceProvider` and `IDeviceClientSource` to pass as `MobileOptions.Provider`. It is a preview: it attaches to an app that is already running, and the device-side verbs are not there yet. What it does:

- `DevFlowAgents.AcquireAsync` finds the agent (`DevFlowAgentsOptions.Port`, else the one agent of the platform and `AppName` a running DevFlow broker lists at port 19223, else port 9223), waits `ConnectTimeout` (60 s) for its status, checks the platform (`status.device.platform`, where the agent writes it) and the app's package id against the target, and claims the agent's mutation lease as holder `e2e`, so the DevFlow Inspector and the MCP server see who drives the app. The agent answers a claim with 200 and says who holds the lease; one another host holds fails the run naming the holder. The lease travels to the worker in `DeviceLease.Client` (`host`, `port`, `leaseId`, `label`). Release gives the lease back and leaves the app running. A worker without a binding finds the agent on its first call, with the platform `devices.boot` names, and claims a lease of its own there. The broker is never started from here. One agent is one running app, so a target with more than one worker slot is `INVALID_CONFIG`.
- The agent lets a lease lapse ten seconds after the holder was last heard from, and refuses a mutation under a lapsed lease with 409 `reason: lease`. So, as Microsoft's own `AgentClient` does, every request that changes the app claims the lease again first (a claim the holder has is a heartbeat). A 409 `lease` on an action names the holder from the agent's `details`, or says the lease lapsed when there is none.
- `capture.snapshot` reads `GET /ui/tree?envelope=true` and flattens it into the snapshot the engine projects. The agent answers 409 `capture-changed-during-read` when the screen moves during the read, as it does while an animation runs, so the tree read and the hit-test are tried up to four times with a short wait before they fail. MAUI types become agent-device kinds (`Entry` is `text-field`, `Label` is `static-text`, `Switch` is `switch`); a type without a mapping keeps its name in kebab case (`vertical-stack-layout`), and the agent's own `link`, `heading`, and `listitem` roles win over the type. The `AutomationId` is the identifier `GetByTestId` reads. A field's text is its value; a password field reports `password: true` and no value, because the agent writes `[REDACTED]` in place of the text and never sends the plaintext. A switch, check box, or radio button reports `checked`. `displayed` and `opacity` give `visibleToUser`. The viewport is the window's bounds. `interactiveOnly` keeps the interactive, labelled, and identified elements and re-parents their children.
- Actions carry the element id and the `captureEpoch` of the tree the ref came from: tap (a tap at a bare point hit-tests the point first, `GET /ui/hit-test`, since the agent's tap takes an element), double tap (`gesture doubletap`), long press (`gesture longpress`, 1 s by default), fill, clear (a fill with empty text), type (the agent's `key` with `text` on the field that has the focus, read off a fresh tree, and `key: "text"`, a name that is no key, so a typed `delete` or `enter` is appended rather than pressed), Enter (`key` on the focused field), a screen scroll (`gesture swipe` on the page the other way, half the viewport by default), a node swipe and scroll, a pan, back (`POST /ui/actions/back`, which pops the navigation, a modal, or a Shell route), the app's theme (`PUT /device/app/theme` for `device.setAppearance`), the foreground app (the agent's status), and screenshots (`GET /ui/screenshot?scale=native`, with the logical size from the window's bounds).
- `apps.open` checks that the agent runs the app the target names and answers its identity. A relaunch, launch arguments, deep links, install, close, home, alerts, orientation, folding, the clipboard, the keyboard dismiss, hover, a drag between nodes, a long press or pan at a bare point, and every device setting but the theme are refused as `UNSUPPORTED_OPERATION`, which a test sees as `UNSUPPORTED_CAPABILITY`. `sessions.close` does nothing. `settle` options are ignored: the engine settles on observe. `normalizeStatusBar` is ignored.
- Errors: a 409 (a stale capture, a changed tree), an element the agent does not find, or a ref the newest tree does not have is `COMMAND_FAILED` with `reason: ref_not_found`, a retryable `NODE_STALE`; a 501, a 404 that names no element, and the `not_supported` and `unsupported-capability` codes are `UNSUPPORTED_OPERATION`; a mutation lease another host holds names the holder; an agent that does not answer is `SESSION_NOT_FOUND` (`INVALID_STATE`), with the hint that the app may not be running. The agent answers `{ success: false, error, reason }` rather than the RFC 7807 body its spec shows, so both shapes are read.
- `E2E_DEVFLOW_TRACE=1` prints each call to the agent (method, URL, status) to stderr, since loopback calls skip a system proxy such as Proxyman. Bodies are not printed: they hold typed text.
- The sample (`samples/MobileApp`) registers the agent under `#if DEBUG` and runs the same tests with `E2E_MOBILE_PROVIDER=devflow` against the app you launched. The two tests that send the app to the background or relaunch it are inconclusive in this mode.
- The package is in CI's pack step but not in the release workflow until the device-side verbs land. Not verified against a running app: every wire detail was read from the agent's source and spec in `dotnet/maui-labs` at `main` (the `0.1.0-preview.13` packages). The unit tests use a fake agent. Among the things to check on a device: the window bounds as the viewport on iOS and Android, whether `role` is set on MAUI elements, the key action with `text`, the lease body, and the broker list.

## WinApp engine (not in upstream)

`E2E.WinApp` drives a Windows desktop app through Windows UI Automation, with the library behind the `winapp ui` command of the Windows App CLI (`Microsoft.Windows.SDK.BuildTools.WinApp.UIAutomation`), in the test's own process. Upstream has no desktop engine, so every type here is .NET-only. The package follows the shape of `E2E.Mobile`: `WinAppEngine` is the `IEngine` (`Platform` `windows`, capabilities observation, actions, keyboard, scroll, screenshot, and pinned app; no location, history, video, or tap modifiers), `WindowSession` the `IEngineSession`, `UiaProjection` the projection into the shared node model, `WindowActions` the action mapping, `WindowKeys` the key grammar, `WinAppErrors` the error table, `Window` the fixture, `WinAppTools` the agent tools, and `WinAppTargetEngine` the one that reads a `TargetConfig`. The library is reached through one seam, `IWindowDriver`, whose only implementation, `UiAutomationDriver`, is the only type marked `[SupportedOSPlatform("windows")]`; the rest of the package builds and is unit-tested on any platform (`tests/E2E.WinApp.Tests`, with a scripted driver). What it does:

- A `windows` target takes `app.appPath` (the executable to launch, relative to the config folder; `E2E_WINAPP_APP_PATH` overrides it) and `app.bundleId` (the process name). With a path the engine launches the executable itself (`WindowProcess`: no shell, `ArgumentList`, stdout and stderr pumped into the attempt's app log, a visible top-level window awaited within `LaunchTimeout`, the process tree killed on timeout, cancel, or close). With a name alone it attaches to the running app and never ends it. `app.open()` has no URL to open, so it relaunches the app; `restart` and `clearState` relaunch too, and nothing is deleted. A URL passed to `open` is `UNSUPPORTED_CAPABILITY`.
- An observation inspects the main window and every other visible window of the process (a WinUI flyout, menu, or combo box list opens in a popup window of its own), nests the flat element list the library returns by depth, and projects UI Automation control types onto the browser roles (`Button` is `button`, a `ToggleSwitch` class is `switch`, `Edit` is `textbox`, a `PasswordBox` class is a secure `textbox` with no value, `List`/`ListItem`, `ComboBox`, `Tab`/`TabItem`, `Window` is `window` for the app window and `dialog` for a `ContentDialog`, popup, or flyout; an unmapped type is its name in lower case). The test id is the `AutomationId`. Boxes are logical pixels, relative to the main window, read through the window's DPI. Refs are the library's selector slugs, bound for the session in a bounded list, since UI Automation identity is stable across inspections: an element the library no longer finds is `NODE_STALE`.
- Actions prefer the control's own pattern: tap invokes, selects, toggles, or expands an invokable control and clicks the middle of any other; fill and clear use the value pattern and fall back to focus, `Ctrl+A`, and typed text for a control that refuses it (a `RichEditBox`); press and type focus the control, bring the window forward, and send keys through `SendInput`, which reaches the foreground window only (WinUI controls are windowless and drop posted messages); a window that cannot come forward is `NOT_ACTIONABLE`; select expands a combo box, observes again, and selects the option by name, value, or automation id; check and uncheck use the toggle pattern (a radio button is selected and cannot be unchecked; nothing is sent when the state already matches); a swipe turns the mouse wheel over the node for up and down, and uses its scroll pattern for left and right or when the desktop cannot take input. On the screen it turns the mouse wheel over the largest scrollable control (the pattern steps by a share of the whole extent, too coarse to land a row of a long virtualized list in view; six notches move a screen or so), scrolls that control by pattern when the desktop cannot take input, and turns the wheel over the window when there is none (up and down only: a sideways swipe with nothing to scroll is `NOT_ACTIONABLE`). A sensitive fill never puts the value in a message. The session also offers hover, long press, drag, a right click, and typed text.
- A screenshot is the main window, encoded as PNG by the package's own `PngEncoder` (the CLI tool strips the Skia natives), with every secure field painted black; a secure field without a box withholds the image.
- `Window` is the fixture: `OpenAppAsync` (the app under test, with `Relaunch`, or another running app by name), `CloseAppAsync`, `ForegroundAppAsync`, `ListWindowsAsync`, `ResizeAsync`, `MaximizeAsync`, `RestoreAsync`, `MinimizeAsync`, and `AlertAsync`, which answers the dialog the newest observation saw: accept presses its `PrimaryButton` (else a button named OK, Yes, Confirm, Accept, Save, or Continue), dismiss its `CloseButton` or `SecondaryButton` (else sends Escape). `WinAppTools.Create(engine)` gives the agent `open_app` and `alert`, scoped to `windows`.
- Errors: a launch that fails or shows no window is `ENVIRONMENT_UNAVAILABLE`; a vanished element is a retryable `NODE_STALE`; an offscreen control, a refused value, and a lost foreground are `NOT_ACTIONABLE`; an app the engine cannot find is `INVALID_STATE` (with the hint to call `app.open()`); anything else the library reports is `ENGINE_FAILURE`. A caller's cancel is `CANCELLED`. The engine never produces `OPERATION_TIMEOUT`.
- `e2e explore` and `e2e mcp` take a `windows` target (`TargetEngines.Create` gets a `windows` factory the way it gets a device one; `WindowsTargets` in the CLI builds the engine on Windows and is `INVALID_CONFIG` on another host). Pattern actions work with the window anywhere; keys, clicks, drags, and the wheel need an unlocked, interactive desktop with the window in the foreground.
- Not there: `App.BackAsync` (`UNSUPPORTED_CAPABILITY`: a desktop app has no history), video, tap modifiers, popup windows in screenshots, a deep-link tool, and the clean-up of the app's data on `clearState`. A packaged (MSIX) app starts through a broker and exits at once, so it is attached by `app.bundleId`, not launched.

## TestMu

`TestMuBrowsers` (the `E2E.TestMu` package, namespace `E2E.TestMu`) is the port of upstream's `testmuBrowsers()` (`packages/testmu/src/browsers.ts`, with `dashboard.ts` and `web.ts`, commit `92f8cb0`), ported in part. It is a `WebEngineOptions.Browser` provider for the TestMu AI (formerly LambdaTest) web grid. Upstream's mobile device provider is a separate part of the same package (see [TestMu mobile](#testmu-mobile)). Taken from upstream: the Edge `--user-data-dir=remote-debug-profile-edge` entry in `browserOptions` (appended to the given ones, kept if a `--user-data-dir=` is already there), the `idleTimeout` default of 600 seconds, the `project` default of `e2e`, the session name `e2e-<run id>-<target>-<slot>` (a per-attempt lease is `e2e-<run id>-<target>-attempt-<attempt id>`), the `Windows 11` default for `Platform`, the credentials read trimmed with a blank value counted as unset (the error names each missing variable), and the validation of `Capabilities` at construction (`INVALID_CONFIG` for a nested `LT:Options`, `browserName`, `user`, `accessKey`, `name`, a `browserOptions` that is not an array of strings, and a number JSON cannot encode). Not taken: the `/puppeteer` CDP URL (the port keeps the Playwright-protocol endpoint, below), the `browserName` check (the port also lets `pw-chromium` through), and the unknown-key check (a record has no unknown keys). The port keeps the seam's names (`IBrowserProvider`, `BrowserLease`) and adds only the provider, `TestMuBrowsers`, and its options record, `TestMuBrowsersOptions`. Only the web grid is covered; TestMu's real devices are not. Differences from a provider like upstream's `kernel`:

- It calls no TestMu API. `AcquireAsync` builds `wss://cdp.lambdatest.com/playwright?capabilities=<JSON>` from `browserName`, `browserVersion`, and `LT:Options` (`platform`, `build`, `name`, `user`, `accessKey`, and the options that were set). The grid starts the session when the engine connects. The lease's `Protocol` is `Playwright`: the grid answers Playwright's own protocol on this URL, not CDP, so the engine dials with `Chromium.ConnectAsync` and opens its own browser context, because the browser has none. `ReleaseAsync` calls nothing, because the grid ends a session when its connection closes (checked against a real account). `SweepAsync` is the interface default.
- The TestMu dashboard shows these sessions without a Passed or Failed mark. TestMu marks a session through its Automation API or a `lambdatest_action` call, which needs the test result, and e2e passes no test result to a provider (upstream's `BrowserReleaseContext` has none either). The provider also does not look up the session id.
- The credentials are `LT_USERNAME` and `LT_ACCESS_KEY`, or the aliases `TESTMU_USERNAME` and `TESTMU_ACCESS_KEY`, read from the run's environment. The access key is part of the endpoint, so the lease id is the session name (`e2e-<run id>-<target>-<slot>` or `e2e-<run id>-<target>-attempt-<attempt id>`), which is what progress lines print. The engine puts no endpoint in an error or a log line, and Playwright drops the query string from the URL it prints when a `ws://` or `wss://` connection fails, so a refused connection does not show the key (a test checks it). Each lease endpoint is about 650 bytes, and a worker's leases travel in one environment variable capped at 16384 bytes, so a target with more than about 20 worker slots fails at prepare.
- Checked against a real account: `ConnectOverCDP` on this URL fails with `Protocol error (Browser.getVersion)`, `Chromium.ConnectAsync` works, and closing the connection ends the session. `TestMuLiveTests` repeats that through the engine and reads the session's end from TestMu's Automation API. It is skipped without `LT_USERNAME` and `LT_ACCESS_KEY`. Mobile devices are not covered.
- Behavior change: a `Capabilities` entry named `name`, `user`, or `accessKey` used to replace the provider's value. It is now refused with `INVALID_CONFIG`, as upstream does.
- `TestMuBrowsersFunctionTests` (`Browsers/`) ports the `it`s of upstream's `browsers.test.ts` for the Edge flag and the validation. Two are partial (`Partial_` prefix): the Edge `it` that also checks upstream's build (`run-1`; the port's is `e2e-<run id>`) and `browserVersion` inside `capabilities`, and the rejection `it.each`, of which the rows for `user`/`accessKey`, `name`, nested `LT:Options`, `browserName`, `browserOptions` (a string, `[1]`, null) and a value JSON cannot encode are covered. The `project` and `idleTimeout` defaults are checked in the .NET-only `TestMuBrowsersTests`, because the upstream `it` that checks them also checks the `/puppeteer` URL and the `Windows 11` default together with `build: run-1` (the port's build is `e2e-<run id>`). The `it`s for the session name and for a missing or blank credential are ported. Not ported: the `/puppeteer` URL (the port's endpoint differs), the lease id without spaces, `undefined` values keeping the defaults (C# has no `undefined`), the unknown-key, `browserName`, non-object `capabilities`, Date, Map, function, BigInt and cycle rows (a typed record and `JsonNode` cannot hold them), the log line (the port logs nothing), the credentials taken from `process.env` (a test would change the process environment, which the live test reads). The other `TestMuBrowsersTests` and `TestMuLiveTests` are .NET-only, in `tests/E2E.TestMu.Tests`.

## Browser install command

Upstream's `e2e-web` command (`packages/web/src/cli.ts`) has one subcommand, `install`. It runs the pinned Playwright CLI. The port has it as `e2e install [chromium|firefox|webkit ...] [--with-deps]`, in the tool that already ships the Playwright driver. It installs Chromium when no browser is named, forwards the options before the browsers, exits with the Playwright code, prints usage for `-h` or `--help` anywhere, and exits 2 for an unknown option or browser. As upstream, the install runs with `PLAYWRIGHT_SKIP_BROWSER_GC=1` unless the user set it. The engine launches the browser `WebEngineOptions.BrowserName` names (Chromium, Firefox, or WebKit; Chromium by default). Upstream's `browser` option is a name or a provider; C# has no such union, so the port keeps the provider in `Browser` and the name in `BrowserName`. `Connect` and a provider attach over CDP, so `Connect` with another browser is `INVALID_CONFIG`.

Upstream's command lives in the web package (`e2e-web`, from `@e2e-dev/web`), apart from the `e2e` command. The port is one tool, and `WebEngine` is in the `E2E` package, so the command is `e2e install` in `E2E.Cli`, the one place the Playwright driver ships. The code follows upstream's split: `E2eWebCli.MainAsync` is `main` and `CliIo` is its `CliIo` (`E2eWebCli` is named for the command; a method called `Main` would be taken for an entry point), `WebEngine.RunPlaywrightCli` is `runPlaywrightCli`, and `BrowserConnection.BrowserNames` and `IsBrowserName` are `BROWSER_NAMES` and `isBrowserName`.

Not ported:

- A command named `e2e-web`, and `npx`, `bunx`, and `pnpm exec` usage lines. `dotnet e2e install` is the local tool form.
- Upstream's exit code 2 for a missing or unknown command. `e2e` exits 1 for both, as it does for every command.
- Forwarding SIGINT and SIGTERM to the installer and the 128-plus-signal exit code. `Microsoft.Playwright.Program.Main` runs in this process. Ctrl+C in a terminal reaches its driver in the same process group; a SIGTERM sent to `e2e` alone does not.
- `install.test.ts` (`ensureBrowsersInstalled`) is the first-launch install of the engine, not the command. The port covers it in `E2E.Tests/Install`, and upstream's own checks of the installed-browser cache and of the run's environment have no counterpart: the port leaves that to Playwright's install (see [Web engine](#web-engine)).

## MCP server

Ported from upstream `packages/e2e/src/mcp` at commit `ee901b333ed12352418dfb07bda5eafe32e71c8d` (`docs(agents): show several personas running one suite (#1258)`), apart from what is listed below. `e2e mcp` serves over stdio with the server name `e2e`, the tools, resources, and logging capabilities, and upstream's four fixed tools with their names, descriptions, and closed argument schemas. Stdout carries only the protocol; every other write goes to stderr, and the MCP SDK logs nothing. The flags are `--config`, `--target`, `--headed`, a hidden `--headless`, and `--max-sessions` (1 through 16, default 4). A session is headless by default; `open_session` takes `headed` to show the browser or hide it, and `--headed` makes headed the default for a session that does not say (upstream commit `dc2afca`). A bad command line exits with 2, a disconnect or a signal with 0, and an unexpected error with 1. The resources `e2e://guide` and `e2e://guide/<topic>` serve the bundled skill; an unknown topic fails with `UNKNOWN_TOPIC`.

A session is an attempt on the config's target with an engine of its own: a Chromium `WebEngine` for a `web` target, or a `MobileEngine` for an `ios` or `android` target (see Device sessions below), or a `WinAppEngine` for a `windows` target (see [WinApp engine](#winapp-engine-not-in-upstream)), so parallel agents each drive their own browser, device, or app (a `windows` target with only `app.bundleId` attaches to one running app, which they share). `open_session` loads `e2e.config.json` fresh, claims the config (`CONFIG_IN_USE` for another config while a session is open), and fails `UNKNOWN_TARGET` for a target the config does not declare, `CONFIG_NOT_FOUND` for no config, `SESSION_OPEN` when no slot is free. `call` and `tools` name a session, or fail `NO_SESSION` or `SESSION_REQUIRED`. A session ends on `close_session`, after 30 minutes without a call, or after 4 hours. It never reads or writes the replay cache. Every configured secret is a secret of the session: any output, error, log line, and the close summary shows its value by name (`<secret:name>`). `type_secret` fills a secret into an editable field (a password secret needs a password field), and `screenshot` keeps attaching the masked PNG after a fill (upstream #1437): it masks secure fields only, so a value the app shows elsewhere is in the image.

The catalog is what the testing agent's tools do, so a coding agent acts as the model of an `act` does: `observe`, `tap`, `double_tap`, `type`, `press`, `select`, `check`, `uncheck`, `clear`, `scroll_to`, `scroll`, `navigate`, `back`, `screenshot`, `type_secret`, and `locate`. `scroll_to` and `scroll` need `EngineCapabilities.Scroll`, `back` needs `History`, `screenshot` needs `Screenshot`, and `type_secret` needs a `secrets` entry. `navigate` allows `http` and `https` only (`POLICY_DENIED` for any other scheme).

Differences:

- Arguments name a node by its `ref` (`target: "e12"`, from `observe`), as the testing agent's tools do, where upstream uses node ids (`n42`) and a revision. Actions answer with the screen after the action, not with a diff of what changed since the last one. A failed action is an error result: `tap e9 failed: NOT_FOUND: node e9 is not on the current screen; re-observe for the newest refs`.
- The grammar is the port's: `type` and `type_secret` take `text` and `secret`; `uncheck` and `clear` are tools of their own. Upstream's `long_press`, `right_click`, `hover`, `drag`, `upload`, and the point tools (`tap_at`, `hover_at`, `type_at`, `press_at`, `select_at`) have no counterpart in the port's actions.
- `locate` writes the `Screen` call a test uses (`Screen.GetByRole("button", "Save")`) and the port's codes: `NOT_FOUND` and `STRICT_MODE`, where upstream names `LOCATOR_NOT_FOUND` and `LOCATOR_AMBIGUOUS`.
- As upstream, a `locate` with a `status`, `alert`, or `listitem` name that matches nothing points at `Screen.GetByRole(role).Filter(text)` and `Screen.GetByText` (spelled as `GetByRole(role).filter({ hasText })` upstream), and an `exact: false` query is not told to loosen the match again (upstream #1147, `5e9597c`): the advice says "an" before a role that starts with a vowel (`an alert`, `a status`), and for an `exact: false` query it keeps the option in the text call, `Screen.GetByText("Saved.", exact: false)` (`getByText(q, { exact: false })` upstream). The web engine names those three roles from their content, so there the name also matches; the advice still holds, since the text matches either way.
- Test lines (upstream #1317, `9ceb071`): every action answers with the `Screen` or `App` call that repeats it, after the first line of its result, and the read-only `test_lines` tool returns them as a draft test body. The code is C# (`await Screen.GetByRole("button", "Save").TapAsync();`, `Secrets.Get(name)`, `Filter(text)`, `Nth(i)`, `new RoleOptions { Visible = true }`, `App.OpenAsync(path)`), and `SessionTestLines` (`Mcp/TestLines.cs`) is upstream's `SessionTestLines` (`mcp/test-lines.ts`). Differences: the port's tree carries a node's test id, so `GetByTestId` is the last query tried for a node, where upstream reads the id off the live node; the port resolves each locator through the engine's `LocateAsync` (2 s each, binding only the matches, so a device keeps the agent's node ids valid) when the engine has one, else on one fresh look at the screen per node with `LocatorResolver`, where upstream spends one engine resolve on each (the cap of 10 tries stays); the live look comes in the port's resolver order, so the twin of a shadow root is told apart by its place in that order and never by the box it kept; there are no credentials, so a fill names `Secrets.Get(name)` only; a `type` that fell back to the keyboard does not exist, because the port's `type` always fills; a locator tap takes no `modifiers`, so a `tap` or `double_tap` with `modifiers` prints `No test line:`; a `press` has no `times`. The web engine names a list item from its content, so a row is found by that name (`GetByRole("listitem", "Offer B Reserve")`) before it is found by `Filter(text)`. The draft ends with a line that tells the agent to add an `Expect` after each step, where upstream also names the `credentials` and `secrets` imports. The session catalog reads the newest observation from the agent's observation feed, where upstream wraps the step context. Not ported with it: the reserved tool name (the port has no project tools), the telemetry event of an MCP session. The drafted lines run as a test class of a project built in a temporary directory with `dotnet test` (`DraftedTestRun`), where upstream runs them with its `runProject`.
- The fixed tools check their arguments with a strict check of the JSON Schema subset tool schemas use, since the .NET MCP SDK does not validate them. The messages are zod's, so an unknown argument reads `Invalid arguments for tool <name>: Unrecognized key: "<key>"`, as upstream.
- The server instructions name `e2e.config.json`, `E2ETest` classes, and `dotnet test` in place of `e2e.config.ts`, `tests/*.e2e.ts`, and `npx e2e run`.
- Writing a test while walking the flow (upstream #1312, `9d884f5`): the server instructions, the `e2e mcp` help text, the skill (`mcp` topic and workflow steps 2 and 3), and the coding-agents guide tell the agent to create the test file before `open_session` and add each step as it takes it: an `Agent.ActAsync` goal before it walks the goal's path, or the `Test line:` an action printed, then, once the outcome shows, an `Expect.That` on a `locate`d locator or an `Agent.AssertAsync`. An action with no repeatable line answers `No test line:` and the reason, and `test_lines` returns the draft so far with a `//` comment for it. The port differs in one way: the workflow names the class per target (`E2ETest` for web, `MobileAppTest` for iOS and Android, `WinAppTest` for Windows) and how each opens its screen (`App.OpenAsync(path)`, `Device.OpenLinkAsync` or the launch screen, the relaunch `WinAppTest` does before each test when the target names `app.appPath`, else attaching where the walk left off). That per-target split is .NET-only. The coding-agents guide has no "How an agent writes and runs a test" section or separate MCP server and reference pages, so only its "Let the agent use the app" paragraph changes.
- The guide has upstream's eight topics, written for .NET, plus `writing-tests-nunit` and `writing-tests-xunit`, one per test framework. `explore` describes `Explore.ExploreAsync`, and `explore` and `bug-bash` say that the bug bash fan-out is not ported.
- The 2026-07-28 MCP revision deprecates logging. The server still declares it and sends its log lines, as upstream does.
- The config declares one target, so `TARGET_REQUIRED` cannot happen. A session's engine is its own, so sessions never share an engine instance, and `ENGINE_IN_USE` happens only for a device (see Device sessions below). The credential registry upstream keeps process-wide has no counterpart (the port has no `credentials`).
- The `e2e` tool ships the Playwright driver of every platform (about 215 MB) and none of the SkiaSharp native libraries, since it never compares screenshots. Chromium installs on the first session, as for a test.
- Device sessions: `open_session` on an `ios` or `android` target builds a `MobileEngine` on a local simulator or emulator (see [Explore](#explore)). The catalog leaves out `navigate` for an engine that declares `PinnedApp`, as the engine has no URL to open; before the first observation the session launches the pinned app fresh (`TargetEngines.LaunchesPinnedApp`, then `App.OpenAsync`), as upstream's `launchesPinnedApp` does (upstream #1252, `3bd32ef`). The summary adds `App: <bundleId or appPath>, launched fresh.`, and the `open_session` description names the pinned app. It installs no build, so a local device target needs `app.bundleId`. The launch is bounded by the session's time limit, as upstream bounds it by the attempt's timeout, and a cancel of the request during the launch surfaces as `CANCELLED`. A device runs one app, so a second session on a device target fails with `ENGINE_IN_USE` (upstream's code for two sessions on one engine instance; the port builds an engine per session, so `SessionRegistry.ClaimEngine` claims the device, .NET-only) until the first closes. Hosted devices are not ported yet.  A `windows` target builds a `WinAppEngine` the same way (`WindowsTargets.Create`, `E2E.Cli`), on Windows only (`INVALID_CONFIG` elsewhere), and launches the executable `app.appPath` names or attaches to the process `app.bundleId` names before the first observation.

Not ported:

- `start_recording` and `stop_recording` (Kernel video), the project's own tools (`defineTool`, `toModelOutput`), custom engines, mobile tools, and per-session telemetry.
- Redaction of what user code prints: a config is JSON, so no user code runs in the server.
- `e2e init` registers the server (see [Coding agents](#coding-agents)); by hand, use `claude mcp add e2e -- e2e mcp` or a `.mcp.json` entry.

## Agents

`E2ESessionOptions` describes the default agent with `Model`, `Judge`, `AgentExecutor`, `AgentSystem`, `AgentTools`, `AgentContext`, `MaxSteps`, `MaxModelCalls`, `JudgmentTimeout`, and `ProviderOptions`, and names the others in `Agents` (an `AgentOptions` per name). `E2ETest` fills both from `agents.<name>` in `e2e.config.json`. A call picks an agent with its `Agent` option; an empty or unknown name throws `INVALID_ARGUMENT` (`unknown agent "x"; configured: default, ...`). Each agent starts from the defaults and inherits nothing from another. Settings are checked when the session starts and fail with `INVALID_CONFIG`.

- A test or a class picks the agent for its calls with `[Agent("name")]` (upstream's `agent` option of `test` and `describe`). The closest pin wins: a call's `Agent`, the method, the class, a nested class's enclosing class, then `E2E_AGENT` (the port's `--agent`, one name; a pin wins over it, as upstream). An unknown name fails the test with `INVALID_ARGUMENT` when the session starts, where upstream fails at collection. `[AgentContext("...")]` is upstream's `agentContext`: the layers join outer to inner with newlines and follow the agent's own `context`, for every agent a call picks, and the cache key sees the joined text. .NET-only symbols: `AgentAttribute`, `AgentContextAttribute`, `E2EFixture.RunAgent`, `E2ESessionOptions.Agent` and `TestAgentContext`, and `TestAgentOptions` (internal). Not ported: a list of agents (`agent: ['buyer', 'admin']`, one result per agent), because NUnit and xUnit have no collection step to fan a test out; the serial-group and setup-test rules that go with it; and `--agent` listing several names.

- `judge` judges `assert`, `waitFor`, and `extract`, and defaults to the model. `act` always uses the model
- `system` is appended to the built-in act rules. Judges never see it
- `context` (at most 16384 UTF-8 bytes) is told to every model call: after the act rules as `Project context:`, and to judges inside `<project-context>`
- `maxSteps` and `maxModelCalls` are 1 through 100, 25 by default
- `judgmentTimeout` (30 s) bounds `assert`, `waitFor`, and `extract` unless the call sets `Timeout`. A per-call timeout must be positive; a `waitFor` interval is 100 ms through 60 s
- `providerOptions` is a dictionary of JSON objects by provider. It rides every `ModelRequest`, and `OpenAiCompatibleModel` adds the fields under its `Provider` key (`openai` by default) to the chat-completions body as given, so write the wire names (`reasoning_effort`, not `reasoningEffort`). It cannot replace `model`, `messages`, or `tools`. Every other client does the same with its own key (`anthropic`, `google`, `bedrock`, `azure`, `xai`, `openrouter`, `gateway`) and refuses its own core fields. As upstream, requests to OpenAI (and Azure over Responses) carry `store: false` and a prompt cache key per system prompt, and Anthropic requests carry cache breakpoints on the system prompt and the newest message; provider options win over both
- `assert` and `extract` make one model call and one repair round. `waitFor` judges at once, then again only after `Interval` and on a changed screen, and every call, repairs included, counts against `MaxModelCalls`. It ends `STEP_TIMEOUT` (`waitFor timed out; last judgment: ...`) or `STEP_BUDGET_EXHAUSTED` (`waitFor exhausted its model-call budget; last judgment: ...`)
- As upstream, the judge prompt says a value shown in more than one place holds only when every place agrees, unless the statement names the place or is about some item among several. The wording follows upstream, with "instruction" as "statement". The judge answers with upstream's `agent-judgment-2` object (see below)
- **Judgment grammar** (`Agent/AgentProtocol.cs`, internal; upstream's `agent/protocol.ts`). `assert` and `waitFor` judge through structured output, as upstream does: the model answers one `agent-judgment-2` object (`protocolVersion`, `explanation`, then `verdict`: `holds`, `fails`, or `inconclusive`) that `AgentProtocol.ValidateJudgmentResponse` checks. `holds` passes, `fails` is `ASSERTION_FAILED`, `inconclusive` is `ASSERTION_INCONCLUSIVE`. The judge has no `done` tool, no tool at all. An answer that is not JSON or does not match gets one repair round (a `<previous-attempt-rejected>` turn with the validation issue), then `MODEL_OUTPUT_INVALID` (`The judge did not answer with an agent-judgment-2 object: ...`). `AgentProtocol.JudgmentSchema` is upstream's `JUDGMENT_SCHEMA`, with `explanation` before `verdict`. `ModelRequest.Schema` and `SchemaName` are upstream's `ModelCall.schema` and `schemaName`, .NET-only in their place: the port's models take a `ModelRequest`, not a `ModelCall`. **Breaking for a custom `IAgentModel`**, which must honor `Schema` (return the JSON object as `ModelResponse.Content`; `Tools` is empty). The providers: chat completions send `response_format` `json_schema`, Responses `text.format`, Google `generationConfig.responseMimeType` and `responseJsonSchema`; Anthropic and Bedrock, which have no such field, offer one `json` tool and force it (the AI SDK's own fallback) unless the request thinks, when the tool is only offered. `OpenAiCompatibleModelOptions.JsonSchemaResponseFormat` (.NET-only, default on) leaves `response_format` out for a server that rejects it; the judge's prompt still asks for the object. Chat completions and Responses send `strict: false`, because strict mode refuses `maxLength`; the agent checks the answer itself. `ModelResponses.Judgment` and `ModelHttp.StructuredAnswer`/`JsonToolName` are .NET-only (a scripted judge answer; the forced-tool answer as content). Not ported: upstream's `extractSchema` and `validateExtractResponse` (the `agent-extract-2` envelope). `extract` still answers through its `extract` and `done` tools, so its inconclusive outlet is the `done` tool.
- `ExtractAsync<T>`: the type argument is the schema, in place of a Standard Schema. The judge gets the JSON schema of `T` (`JsonSchemaExporter`), and the answer must deserialize into `T` with required members and nullable annotations respected. A failure gets one repair round with the validation error, then `MODEL_OUTPUT_INVALID` (`extracted data failed schema validation: ...`). A judge that says the data is not shown ends `ASSERTION_INCONCLUSIVE` (`nothing to extract: ...`)
- `tools` (`AgentOptions.Tools`, `AgentTools` on the default agent) are project tools the model is offered beside the agent's own. As upstream's `defineTool`, an `AgentTool` declares `mutates` and `platforms`: a tool is offered only on the platforms it names, and a mutating tool takes an action slot. Its output is redacted and cut at 16384 characters. A name the agent already uses (`observe`, `done`, `navigate`, `back`, `scroll`, `scroll_to`, or a verb) is refused with `INVALID_CONFIG`. Differences: the tool is an `AgentTool` built with its schema as a `JsonObject` and a delegate, since the port has no `defineTool`, AI SDK tool, or `toModelOutput`; a tool that wants upstream's `getToolContext` takes the second constructor, whose delegate gets an `AgentToolContext` (`ObserveAsync`, `AttachScreenshotAsync`), and the first constructor keeps working; and upstream's reserved names for tools it adds elsewhere (`complete_step`, `locate`, the recording tools, `report_finding`) have no counterpart. Upstream records a mutating tool as a gap in the trace, and so does the port: a recording holds an action of kind `tool` with the tool name, a replay runs the actions before it and then hands the step to the model, and the step is never replayed whole. Older versions of this port cannot read that action and run the step live. As upstream, a recording that stops at such a gap (reason `gap`) is not stale: a strict cache run replays what it can and runs the rest of the step live. The recording keeps the tool's name only, never its arguments
- `tap` and `double_tap` take an optional `modifiers` list (`Shift`, `Control`, `Alt`, `Meta`, `ControlOrMeta`) on an engine that declares `EngineCapabilities.TapModifiers`, as upstream's `tap`, `double_tap`, and `right_click` do on an engine that declares `tapModifiers`. The web engine declares it. The device engines and the document engine do not, and refuse the field with `UNSUPPORTED_CAPABILITY`. The held keys are recorded as `modifiers` of the `tap` or `doubleTap` action and replayed from the cache. An entry whose `modifiers` is empty, repeats a key, or sits on another action is a miss (`invalid-entry`). The tools do not close their schemas, so a tool called with a field its engine does not declare is refused by the action, not by the schema. There is no `right_click` tool yet: the web engine has a secondary tap now ([#638](https://github.com/hardkoded/e2e-dotnet/issues/638) tracks the agent verbs).
- `act` also offers a `double_tap` tool, which upstream does not have. Without it, the agent cannot open a control that reacts only to a double-click, such as a TodoMVC label that opens its editor. It runs the locator `doubleTap`, and the replay cache records it as `doubleTap`. Upstream and older versions of this port cannot replay that entry, so they run the step live
- `ActOptions.OnAction` is upstream's `onAction`: a hook that runs after each action once the screen settles, for replayed actions too. The hook is an `ActionHook` delegate returning a `Task`, and the event's `source` is the `ActionSource` enum (`Model`, `Replay`). Upstream's check that `onAction` is a function has no counterpart, since the delegate type says it. A hook that throws fails the step (`ACTION_FAILED`, `agent.act onAction failed: ...`) and leaves the step's recording alone. Upstream takes a screenshot from the hook with `app.screenshot`, which is not ported, so the port's tests record the events and the screen the hook reads. Tests: `agent-act-on-action.test.ts` is `AgentActOnAction/` (6 of 6, plus one .NET-only test for a replayed step whose hook never completes; the first is renamed and partial: it does not check that each hook step holds one screenshot artifact. The others record the hook's events in a list where upstream takes an `app.screenshot` step, and check the same behavior). The `act-validation` `it` "takes an onAction function and refuses any other value" is skipped: a delegate cannot be anything but a function. .NET-only: `AgentException.FromActionHook` (internal), where upstream has an `ActionHookError` subclass, because `AgentException` is sealed
- `act` params are checked as upstream: JSON-safe values, at most 32 levels deep, no cycle, and at most 64 KiB once a `Secret` is projected to its name and purpose and a `Values.Unique` to its value. The instruction is at most 8192 UTF-8 bytes. Each limit throws `INVALID_ARGUMENT` with the upstream message before any model call. A value reached twice through different paths is not a cycle
- `Vision` on `AssertAsync`, `WaitForAsync`, and `ExtractAsync` is a `VisionMode` (`Off`, `On`, `Only`) in place of upstream's `false`, `true`, and `'only'`, and an undefined value throws `INVALID_ARGUMENT`. `On` sends a masked screenshot beside the tree, and `Only` sends the screenshot alone, with a note that no tree is attached on purpose. The screenshot is sized for the model (long side at most 768 pixels) and its note names the regions masked for security. An engine that captures no pixels or masking the engine cannot prove (fewer masked regions than secure nodes in the tree, or no count at all) takes the image away and the judgment goes on with the tree; `Only` has no tree to go on with, so it fails with `POLICY_DENIED` that names `MASKING_UNPROVEN` or `UNSUPPORTED_CAPABILITY`, before any model call. The judge's system text says an attached screenshot is data, as upstream's policy does. `WaitForAsync` takes a screenshot with each look and counts a changed picture as a changed screen. An inconclusive judgment made from the tree alone ends with the hint to pass `Vision = VisionMode.On`, firm once a judgment of the attempt has received pixels and conditional before ("if the engine captures pixels"), and none when pixels cannot help: the engine declares no `Screenshot` capability, or an earlier request for pixels was degraded. The hint's words name the C# option
- `AssertOptions.Screenshot` (on by default) keeps the redacted viewport after the verdict, a passing one too, under `.e2e/results/<result>/attempt-<n>/screenshots/<n>-assert.png`, and `AgentException.Screenshot` names it on a failed judgment as a path relative to the project root, where upstream names it relative to the artifacts directory. An engine that captures no pixels keeps none. A secret fill does not stop it: the screenshot is the project's own artifact. Taking it never fails the judgment. The port's step record has no `visionInput`, `visionDegraded`, `visionOnly`, or `pixelBytes` on a step, no `vision.pixels` or `assert.screenshot` policy events, and no observation revision in a pixels-only request

- `executor` (`AgentOptions.Executor`, `AgentExecutor` on `E2ESessionOptions` and the fixtures) replaces the built-in agent for `act` and `assert`. The socket is `IStepExecutor`: `Name`, and `Version`, `Cache`, `Model`, and `Judge` with defaults, so a hand-rolled executor writes `Name` and `RunStepAsync(context, cancellationToken)`. The token is upstream's `signal`; the context's `Attempt.CancellationToken` is upstream's `attempt.signal`. `StepExecutorContext` is a class a test can build and override: `Step`, `Attempt`, `Target`, `ReplayedPrefix`, `Model`, `ProviderOptions`, `Ledger`, `AgentContext`, `Budgets`, `Actions`, `ObserveAsync`, `AttachTranscript`, and `AttachScreenshotAsync`. An executor is code, so `agents.<name>.executor` in `e2e.config.json` stays `INVALID_CONFIG` and names `AgentOptions.Executor`. As upstream, `System` and `Tools` are refused beside an executor, and the `Model` and `Judge` an executor brought are the agent's, for the judgments too. An entry that names another is `INVALID_CONFIG` (`agents.default.model (gpt-5.4) and the executor's own model (gpt-5.4-mini) differ; configure the model in one place`). Two models are the same when they are one instance or share a `Name`, where upstream compares the provider and the id
- The `Ledger` text an act reads is upstream's `serializeLedger` over the attempt's step records: `1. app.open passed :: /` per completed step, then `   observed: <handoff>` when it has one, up to 8192 bytes, newest kept, with `[n earlier step(s) omitted]` first. A failed step is in it, with its status. Each label and handoff is stripped of ANSI sequences and control characters and cut to 256 and 700 bytes. A step is recorded for `agent.act`, `agent.assert`, `agent.waitFor`, `agent.extract`, a locator action and `locator.waitFor`, an `expect` matcher on a locator, the browser, or the screen, and `app.open`, `app.back`, `app.restart`, and `app.clearState`. The `Browser` and `Device` fixture calls are steps (see App and browser fixtures); `expect.poll` is not a step yet. The records are internal; no report reads them yet. A replayed act hands later steps the text the replay returns (`Replayed recorded actions.`), where upstream hands them the verdict the recording run wrote, because the port's cache entry keeps no verdict.
- `ToolLoop.CreateToolLoopExecutor` and `DefaultAgent.CreateBuiltInAgent` are public. Differences: `ToolLoopExecutorOptions.Tools` returns a list of `ToolLoopTool` (a `ModelTool` and a delegate that answers a `ToolLoopResult`), where upstream's returns an AI SDK `ToolSet`; `BuildPrompt` answers a string, where upstream's can answer a whole message history; the chassis adds `done`, where upstream adds `complete_step`; there is no `maxTurns` to remove. `ToolLoopHelpers` has `GuardAsync`, `Concluding`, and `ReportHardStop`, and the loop guards every tool call itself. The built-in agent drives the context the runtime builds, so it runs as a step's executor or inside a custom executor that passes its context on, and not on a context built by hand
- The verbs are the ones the port's engines have: `TapAsync` and `DoubleTapAsync` (both take `ClickOptions`, whose `Modifiers` need `Target.TapModifiers`, as upstream's `tap(target, { modifiers })` needs `target.tapModifiers`), `TypeAsync`, `TypeSecretAsync`, `ClearAsync` (upstream clears with `type`), `PressAsync`, `SelectAsync`, `CheckAsync`, `ScrollToAsync`, `ScrollUntilAsync`, `ScrollAsync`, `NavigateAsync`, and `BackAsync`. Not ported, because no engine here has them: long press, secondary tap, hover, drag, upload, the point verbs (`tapAt`, `hoverAt`, `hitTest`), `typeText`, `pressKey`, and `dismissKeyboard`. `Target.Verbs` follows the engine's capabilities: the scroll verbs need `Scroll`, `Back` needs `History`. A node is named by its ref (`new ExecutorTarget("e12")`, the `[ref=e12]` of a line), where upstream names `n42`. Actions and looks run in call order, mutating project tools included, and a mutating `RunToolAsync` body that calls an action or a look waits behind itself, as upstream's does. A verb checks its argument before it takes a slot (`INVALID_ARGUMENT`), but the port has no key grammar, so `PressAsync` takes any non-blank key
- `ObserveAsync` answers `Text`, `Truncated`, `KeyboardVisible`, `Path`, and `Revision`, and with `ExecutorObserveOptions` `Tree` (a list of root `ExecutorNode`s, redacted, with no value or selection on a secure field, a link target absolute and cut as a line cuts it) and `Pixels` (the masked screenshot sized for the model, or `PixelsWithheld`, a `VisionDegradation`). `Revision` is upstream's `revision` (`Observation.Revision`, null when the capture carries none); it has no `Viewport` and no `framePath`, since the port has none. `ReplayedPrefix` carries the actions as the text the hand-off notice lists, `ReplayHandOffReason` adds the port's `ActionBudget` and `InvalidEntry`, and has no `viewport-changed`. A replay that meets `ACTION_MAY_HAVE_COMMITTED` stops as `action-uncertain` and names the action, which the built-in agent's notice repeats. `KeyboardVisible` is upstream's `keyboardVisible` (commit `5fce7b2`): `Observation.KeyboardVisible` carries the engine's measured on-screen keyboard state to `ExecutorObservation.KeyboardVisible`, and the mobile `DeviceSession` sets it from the capture's keyboard fact (`visible` is true, `absent` is false, and an unmeasured capture leaves it null). The web engine measures none, so it is always null there. Not ported: the part of that commit in `@e2e-dev/decision` (`dismiss_keyboard` and the page fingerprint), and the `sdk-types.ts` checks, which the C# types make. Tests: `FixtureRuntime/ProjectToolDispatchTests` and `E2E.Mobile.Tests`' `Engine/ObservationTests`.
- The runtime owns the budgets and the clock. `RecordModelCall` throws `STEP_BUDGET_EXHAUSTED` past `MaxModelCalls`, and a verdict never outranks a hard stop: a passed one over a spent budget, a timeout, or a code-less failure after one ends with the runtime's code. An executor that ignores its token gets one second to unwind after the step is stopped, and then the step settles without it. The closed verdict grammar is upstream's: an empty summary, an unknown code, a passed verdict with a code, or a blocked one without a blockable code is `MODEL_OUTPUT_INVALID`, and so is a runtime code the runtime did not record. A thrown error that is no agent error becomes `ACTION_FAILED`, as upstream's `toAgentError` does, and a cancel by the caller stays an `OperationCanceledException`. The message of a failed or blocked verdict is upstream's `agent.act failed: <summary>` or `agent.act blocked: <summary>` (`agent.assert` for an assert). The step keeps the bare summary as its explanation, as upstream does. A hard stop (`Step timed out`, a spent budget) that ends the step with no verdict, or over a passed or code-less one, has a message with no prefix (the reason, then the verdict's summary if there is one); a coded failed or blocked verdict gets the prefix, also after a hard stop
- `AssertAsync` on an agent with an executor goes to it as a step of kind `Assert`, with the agent's budgets and `JudgmentTimeout`. An assert is never cached, and a passing one verifies the acts before it. `Vision` is refused with `UNSUPPORTED_CAPABILITY`, since the executor decides what its model sees, and `Screenshot` keeps its evidence after the verdict, bounded by the action timeout: a capture that outlives it is dropped and the verdict stands. `WaitForAsync` and `ExtractAsync` keep the judge, which is the executor's `Judge` or `Model`. `ExecutorCache.Off` never replays or records, and takes no look before the step. A step with the cache on that cannot read its first screen (no app opened) still runs, and records nothing
- `TypeSecretAsync` fills a secret the step's params declared, and refuses with `POLICY_DENIED` any other name, a disabled or non-editable field, and a field whose purpose does not fit a password secret. A secret the attempt does not know is `AUTH_CREDENTIAL_UNAVAILABLE`. The built-in agent's `fill_secret` goes through the same check, so its refusals read as the dispatcher's messages and not as `Secret fill refused: ...`. `ExecutorStep.Params` is JSON: a `Secret` is its name and, when set, its purpose, and every string and key that holds a secret value the attempt knows is redacted. `ExecutorAttempt` has the session's `TestTitle` as `TestId`, a fresh id per session, and `Index` as the attempt number minus one; `ExecutorStep.Index` counts the agent steps of the attempt, where upstream's counts every step. `AttachTranscript` and `AttachScreenshotAsync` write under the attempt's results directory (`transcript-<n>.txt`, `screenshots/<n>-<label>.png`), and, as upstream, only under `E2E_DEBUG=1`. `AttachTurns` keeps the step's last 12 turns on the step record, redacted, as upstream's `attachTurns` does, and the tool loop reports every turn it takes with the same clips. Its loop notes cover the events the port's loop has (a reply without a tool call, a shrunk history); upstream's others (a forced tool choice, the wind-down notice, a resent stalled request) have no counterpart. Deliberate difference: upstream clips a turn's text and then redacts it, so a cut can split a secret and leave a part the redactor no longer matches. The port redacts first and clips after, both in the loop and again in `AttachTurns`, which also enforces the bounds itself (the last 12 turns, 8 calls of 200 characters, an outcome of 2048) for any executor. A clip never splits a surrogate pair. The loop does not yet attach its debug transcript. The port has no step events

- `maxObservationBytes` and `maxInputTokens` are upstream's agent keys (`config/agent.ts`), in `e2e.config.json`, on `AgentOptions`, `E2ESessionOptions`, and the fixture. `ResolvedAgent.From` and the config check them as upstream's `boundedInt` does (`agents.default.maxInputTokens must be an integer from 1 through 1000000`; `maxObservationBytes` takes 1024 through 16777216), and the defaults are upstream's 262144 and 64000 (`E2EDefaults`). `ObservationBudget.ObservationByteBudget` is upstream's `observationByteBudget` (`agent/observation-budget.ts`), over `ModelAdapter.TokenUpperBound` and `ImageTokenUpperBound` (upstream's `adapter.ts`), both in UTF-8 bytes. `SnapshotText.Render` cuts the screen at that budget as `prepareObservation` does: the marker is reserved up front, the first node is always listed, and the first line that would pass the budget ends the screen with `[observation truncated at the resolved observation byte limit]`. A step that cut a screen reports `observationTruncated`. An act cuts each look at `ObservationFeed.Text` (upstream's `byteBudget` in `observation-feed.ts`) around what every turn resends: the context, the prior-step ledger, and the instruction. Upstream redacts each capture once as it is taken; the port renders a look's text when it is read, and keeps the newest rendering only while the attempt's redactor is the one it was rendered under, so a secret registered since is never read from the kept text (`AgentObservation/ObservationFeedTextTests`, .NET-only). A judgment cuts at `Agent.ObservationByteBudget` (upstream's `invocation.ts`), around the system text, the instruction, and a screenshot when `Vision` is on; under `VisionMode.Only` the tree does not reach the request, so only `maxObservationBytes` bounds it. A judgment whose request is still over `maxInputTokens` fails with `STEP_BUDGET_EXHAUSTED` before it is sent (upstream's pre-flight in `sdk.ts`). Differences: the port's tree text is its own format (`Screen (/):` and `- role "name" [ref=e1]` lines), so the header counts against the budget, and upstream's second marker for an engine-cut tree is the port's `(More of the page is off screen. Scroll to reach it.)`, which a byte cut replaces. The act loop is not pre-flighted, as upstream's is not, and the port's tool loop resends its whole history, so a long act can still end in `CONTEXT_OVERFLOW`, which shrinks it. The run's limits (`ResolvedAgent.RunLimits`, upstream's `runLimits`) are the largest any agent allows, and the trace's screens, `screen.tree()`, the failure evidence, and the report's `limits` read them. Upstream's removed-key hints for the agent keys (`timeout`, `maxTurns`, `maxModelTokensPerCall`, `limits`) and the top-level `specVersion` and `limits` are ported. Tests: `AgentObservationBudget/ObservationByteBudgetTests` and `ObservationBudgetWiringTests` (.NET-only), `AgentObservation/ObservationByteBudgetTests`, and `AgentConfig/AgentConfigDefaultsTests` and `RunLimitsTests`.

## Explore

`Explore.ExploreAsync` ports upstream's `explore` (`packages/e2e/src/explore`), the library under `e2e explore`, and `e2e explore` ports the command (see below). An exploration is the planner (`ExtractAsync`), the explorer (the built-in agent with the exploration rules and `report_finding`), and the loop of charters under the exploration's budgets, with upstream's outcome policy: a failed step is not a finding, a step at its limit is neither, three unproductive steps in a row end the run, reported issues fail it, and a run that explored nothing, or whose charters were all blocked, stays blocked. The planner's prompt, the repairs of its answers (padded digit runs, a lone title or charter), and the explorer's rules are upstream's text, with `done` where upstream says `complete_step` and `fill_secret` where it says `type_secret`.

- The port has no runner, so `ExploreAsync` starts one `E2ESession` and returns an `ExploreOutcome`: `Status` (`RunStatus`: `Passed`, `Failed`, `Blocked`), `ExitCode` (0, 1, 2, or 3, from the error that ended the run by upstream's table of agent codes), `Error` (the `E2EException` that ended the run), and `Explore` (upstream's `run.explore` block as `ReportExplore`). A config, agent, target, goal, or budget error throws before anything starts, as upstream does. A cancelled token throws `OperationCanceledException`, where upstream's interrupt is exit code 130.
- A failure while closing the exploration (the engine's `finish` hook, or the session's own release) does not throw and does not replace the outcome: as upstream's runner records it as a run error of phase `cleanup` and folds its category into the exit code (precedence 130, 4, 3, 2, 1, 0), `ExploreOutcome.ExitCode` is the verdict's combined with the cleanup failure's (an engine failure is 3), `Error` is the verdict's error or else the first cleanup failure, and a failure that is not an e2e error is an `ENGINE_FAILURE`, as upstream's `translateProvisioningError` makes it. The findings stay in `Explore`.
- Times are `TimeSpan`s: `ExploreOptions.Timeout`, `ExploreBudgets.Timeout`, and `ReportExploreStep.Duration` where upstream has `timeoutMs` and `durationMs`. The step bounds are `Explore.StepBounds` (1 to 12, 8) and the time bounds `Explore.TimeoutBounds` (3 to 15 minutes, 10).
- Upstream's `ExploreOptions.rawConfig` is `RawConfig`, an `E2EConfig`. Because `e2e.config.json` holds a provider and a model id only, `Agents` gives `AgentOptions` by name over the config's, for a model of your own or a project tool, and `Engine` gives the engine, where upstream's config file holds both. `OnProgress` receives the `ExploreProgress` moments that upstream sends as `explore` run events through `onEvent`; `FindingReported` is upstream's `finding` phase.
- The config declares one target, so there is no choice among several and no notice for it; `Target` only has to name that one (`UNKNOWN_TARGET` otherwise). The port rejects `credentials` in the config, so `Credentials` gives the accounts in code, by name, as `UserCredential`s (`Credentials.User` reads one from the environment). Each travels into every step as the username and the secret `<name>.password` (purpose `password`), and a secret anywhere in the params of an `act`, at any depth, is declared and remembered, as upstream's walk of the params finds it. The size bound of the account inventory, a quarter of the params limit, is upstream's.
- A target's engine is chosen from its platform, a .NET-only bridge: upstream's config holds a live engine handle, and `e2e.config.json` still rejects an `engine` key. `web` is a `WebEngine`. `ios` and `android` are a `MobileEngine` (`MobileTargetEngine.Create`, `E2E.Mobile`) built from `app.bundleId` or `app.appPath` and `E2E_MOBILE_DEVICE`, as for `MobileAppTest`. `windows` is a `WinAppEngine` (`WinAppTargetEngine.Create`, `E2E.WinApp`; the CLI passes `WindowsTargets.Create` as the `windows` factory of `TargetEngines.Create`, which is `INVALID_CONFIG` off Windows) built from `app.appPath` or `app.bundleId`, as for `WinAppTest`. `ExploreOptions.Engine` still wins. The device engine needs Node 22.12 or newer and a booted simulator or emulator. `E2E_MOBILE_PROVIDER=limrun` or `devflow` makes the engine lease a hosted device, as the config of upstream's CLI does with `mobile({ provider: limrun() })` (the port names the provider by variable, like the adapters). Any other value fails with `INVALID_CONFIG`; `E2E.Eas` and `E2E.TestMu.Mobile` are not referenced by `E2E.Cli`, because upstream's CLI loads providers from the config and the port's tool ships only Limrun and DevFlow. Upstream's `openStandaloneAttempt` (`run/standalone.ts`) prepares the engine for one slot of a run of its own and finishes that run when the attempt closes, on every path (`engines.prepare` and `engines.finish`, `run/provision.ts`). The port has the same: `Standalone.OpenAttemptAsync` is `openStandaloneAttempt`, over `Standalone.OpenWorkerAsync` (`openWorker`) and its `StandaloneHost` (`openAttempt`, `close`), and `PreparedEngines` is `provision.ts`'s class of that name. Only upstream's one-shot kind exists: the hosted kind publishes each session for another test runner, and the port's tests run in their own. An engine takes part by implementing `IPreparableEngine` (.NET-only: upstream's engine handle carries optional `prepare` and `finish` members). `MobileEngine` does; `WebEngine` does not, because it leases for the attempt it starts (below). `e2e explore` and `e2e mcp` open their session through the host, so the lease happens when the session opens, never when the engine is built or when `ENGINE_IN_USE` refuses a second session, and `MobileEngine.StartAsync` leases nothing itself. What prepare leaves (the device binding) reaches the worker in `EngineStartOptions.Env`, under the run's own variables. The finish runs once, within the cleanup timeout, and a hook that outlives it is abandoned and reported as `CLEANUP_TIMEOUT` whether or not it honors its token, as upstream does. A finish that fails is an error (`close_session` shows it as a `Cleanup:` line, and `e2e explore` ends with it), because a hosted device bills until it is released. A start that fails or is cancelled after the lease was granted finishes the engine, with a failed finish added to the start's message; a caller cancel surfaces as `CANCELLED` and not as a provider failure; a lease the provider grants after the caller stopped waiting is released where it lands; and the end of the process finishes an engine still held (`AppDomain.ProcessExit`, .NET-only; a killed process is covered by the provider's own time limit, 15 minutes for Limrun). ## Config

`E2ETest` loads the nearest `e2e.config.json` above the test assembly directory, then above the working directory, once per run. Supported keys: `targets` (one entry with `name`, `platform`, and `app` with `url`, `command`, and `readyUrl`), `timeout`, `launchTimeout`, `actionTimeout`, `assertionTimeout`, `cleanupTimeout`, `retries`, `agents`, `cache` (`mode`, `dir`, `strict`), and `secrets`. Defaults, the CI cache demotion to `read-only`, `E2E_SECRET_<NAME>` overrides, the 6 code point secret minimum, and `INVALID_CONFIG` for unknown keys follow upstream.

`app.url` is normalized as upstream does, with `System.Uri` instead of WHATWG: a missing scheme becomes `https://`, or `http://` for a loopback host. Userinfo, a query, a fragment, a scheme other than http(s), and plain HTTP on a non-loopback host are `INVALID_APP_URL`, with upstream's messages. A base URL set in code (`E2EFixture.BaseUrl`, `E2ESessionOptions.BaseUrl`) follows the same rule. Port `0` on `127.0.0.1` or `[::1]` asks for a free port and needs an `app.command` to start the app on it (`INVALID_CONFIG` without one, or with `reuseExisting`); any other host with port `0` is `INVALID_APP_URL`. A base URL set in code with port `0` is `INVALID_CONFIG`, since only `app.command` starts an app on a free port. Keys of the old .NET shape (`app`, `engine`, `agent`, `timeouts`) fail with a hint to the upstream key.

`app.command` and `app.readyUrl` port upstream's `config/command.ts` and `config/app.ts` (`CommandConfig`, `Command.Normalize`, `TargetApps.ResolveTargetApp`), and `ManagedProcess` ports `run/managed-process.ts` (readiness polling, the preflight probe and `reuseExisting`, the startup-failure tail of `command.log`, `inheritEnv`). `executable` is started with an argument list, never a shell. `{port}` expands in `args`, in `env` values, and in `readyUrl`, and a `url` on port `0` takes a free loopback port (`AppPorts.AllocateTargetPorts`, upstream's `allocateTargetPorts`). The first test, `e2e explore`, or `e2e mcp` session that needs the command starts it, through `Provision.StartDeclaredProcessesAsync` and one process-wide `SharedAppProcesses` pool (upstream's `startDeclaredProcesses` and `SharedAppProcesses`): they share one instance, and it stops when the last holder releases it. A test holds it for the run (`E2EFixture.StartSessionAsync` calls `RunApps.StartAsync`); `Explore` and the MCP session hold it for their own life (`RunApps.AcquireAsync`) and release it when they close. The tests' hold ends with the run fixture (`E2E.NUnit.E2ERunFixture`, a `[SetUpFixture]` base, or `E2E.XUnit.V3.E2ERunFixture`, an assembly fixture, both .NET-only: a .NET test project has to register them, since neither framework runs a hook from a referenced library), and without one it lasts until the process ends, where `ManagedProcess.KillManagedProcessGroups` takes it down on the way out; on Windows the process runs in its own job object (`ProcessJob`, .NET-only), which ends it and what it started when it is stopped, and when this process is killed outright, as a test host is once its run ends. On Unix a descendant is read with `pgrep -P` when the app is stopped, so one that outlives a leader that exited earlier is not found. The app command differs from upstream's in these ways:

- There is no runner, so a command starts once per test process (a .NET-only holder, `RunApps`), not once per run. Two processes that declare one command, such as `dotnet test` and `e2e mcp`, each start their own, so give a shared app a fixed port and `reuseExisting`. Upstream's `SharedAppProcesses` pool (`ProcessPool.cs`), `declaredCommands` (`DeclaredProcesses.DeclaredCommands`, over a target's name and resolved app, since the port has no `ResolvedTarget`), and `startDeclaredProcesses` (`Provision.StartDeclaredProcessesAsync`, with `ProcessPools.Unshared` for upstream's `UNSHARED`) are ported, and share the instance inside one process. The engine `prepare` hooks that `startDeclaredProcesses` shares a provision with are not ported. A caller whose token is cancelled leaves a shared start with `OperationCanceledException`, where upstream throws `CANCELLED`. A target whose command ended while it was held is started again by `RunApps` (.NET-only: the holder outlives its callers), on a new port when it asked for a free one.
- A started process is stopped with `SIGTERM` and then `Process.Kill(entireProcessTree: true)` after `shutdownTimeout`. On Windows, which has no signal to ask a process to stop, the first step is the kill. There are no process groups: on Unix the descendants are read with `pgrep -P` before the leader is signalled, then each is sent `SIGTERM` and, after `shutdownTimeout`, `SIGKILL`, so a descendant that outlives its leader's exit on `SIGTERM` is still ended. The two `managed-process` integration tests about that (`stops a surviving child after the command leader exits on SIGTERM`, `lets a child finish its shutdown after the leader exits`) are ported and return at once on Windows, as upstream skips them there. `stdout` and `stderr` are read together into `log` (or dropped when there is none), line by line as the process writes them.
- A cancelled token ends `ManagedProcess.StartAsync` by throwing `OperationCanceledException` after taking the process down, where upstream's `start` returns and the caller reads the signal. `startupTimeout` and `shutdownTimeout` are `TimeSpan`s (`CommandConfig.StartupTimeout`, `ShutdownTimeout`), and a value over 2147483647 milliseconds, which a .NET timer cannot wait, is `INVALID_CONFIG`. A readiness probe still waiting when the process exits ends there.
- JSON has no `secrets.get()` handle, so the message that names one for a string value of `args`, `env`, or `url` is not reachable, and an `env` entry of `null` stands for upstream's `undefined`. `command.log` containment resolves symlinks as `relativeToProjectRoot` does (`Paths.RelativeToProjectRoot`). An app key outside the port's set is named in the port's own words (`unknown targets[0].app key "readyURL"`), where upstream says `target "web" app has unknown key`; the command's own keys use upstream's message.
- The resolved app (`ResolvedApp`) has `Base`, `PortRequest`, `Site`, `Environment`, `Identity`, `BundleId`, `AppPath`, `LaunchArguments`, `Permissions`, `Command`, and `ReadyUrl`, as upstream's. `Site` is `Urls.SiteOf`, `Environment` defaults by `Urls.IsImplicitTestHost`, and `Identity` keeps the declared `:0`. `AppConfig` (`Identity`, `Environment`, `LaunchArguments`, `Permissions`, with the `AppPermissionState` enum) is the checked declaration (upstream's `TargetAppDeclaration`, read from JSON in `E2EConfig`; the shape errors read `targets[0].app.<field>` where upstream's name the target). `TargetApps.DigestTargetApp` and `Command.DigestCommand` are upstream's `digestTargetApp` and `digestCommand`, but the port has no config digest to put them in, so `config.test.ts` "digests the app a target declares" and the `configDigest` checks of `app-ports.test.ts` compare the app digest alone (partial). Upstream's `engineAppInfo` and `EngineAppInfo` are not ported: the port's engines are built from the target (`MobileTargetEngine`, `WinAppTargetEngine`), not handed its app at `prepare` and `init`. The report's `run.targets[].environment` is still always `test`, not the app's resolved environment.
- Tests: `ManagedProcess/` ports the `it` of `tests/unit/managed-process.test.ts` and `ManagedProcessIntegration/` those of `tests/integration/managed-process.test.ts`, with the program they start (`E2E.Tests.App`) where upstream runs `node -e`; the notice tests wait out a real budget where upstream moves a fake clock. `AppPorts/` ports `app-ports.test.ts` (partial: one target, and no config digest). `Config/` ports the command and `readyUrl` tests of `config.test.ts` and its `identity`, `environment`, `site`, app shape, and app digest tests. `TargetIdentity/` ports `target-identity.test.ts` (the `project id` `describe` is not ported: the port has no `projectId`). `DeclaredProcesses/` ports `declared-processes.test.ts` and `SharedAppProcesses/` ports `shared-app-processes.test.ts` (each target is a name and a resolved app, since the port loads one target per config). `RunApps/` is .NET-only. Not ported, because the port has no runner or target-selection execution path (`targetIds`, `runExisting`): the four `it` of `target-processes.test.ts`, `starts the shared app command of the selected targets once, and nothing for the others`, `copies inheritEnv variables from the environment the run is given`, `rejects an unknown target with its suggestion before starting any process`, and `preserves an initial interrupt before validating target IDs or starting processes`.

Differences:

- JSON has no engine handles or model instances. The fixture's `CreateEngine` chooses the engine, `platform` must be `web`, and `targets` holds one entry. `agents.<name>.model` and `judge` are model ids for the .NET-only `provider` (see [Models](#models)), with the .NET-only `baseUrl` and `apiKeyEnv` beside them. ## Web engine

`WebEngine` launches Chromium (or Firefox or WebKit, per `BrowserName`) through Playwright and builds a semantic tree in the page: explicit roles, the upstream implicit role table (landmarks, lists, tables with rows and cells, dialogs, options, `img alt=""` as presentation unless it has a `title`, a `tabindex`, or a global ARIA attribute, and `role="presentation"` or `role="none"` ignored on a focusable element or one with a global ARIA attribute, `select multiple` as listbox, and the rest), accessible name, text, test id, heading level, and the disabled, checked, expanded, selected, pressed, focused, and hidden states. As upstream, the name reads `aria-labelledby` before `aria-label` and associated labels. Disabled covers `:disabled` (including a disabled fieldset), `aria-disabled="true"` on the element, and `aria-disabled` inherited from an ancestor for the roles it applies to. Checked is the native state for checkbox and radio inputs and `aria-checked="true"` elsewhere; `mixed` reads as not checked. Hidden is what renders, as upstream: `display: none`, a `visibility` other than `visible`, content under `content-visibility: hidden`, and content a closed `details` folds away. A `display: contents` element is shown when a child element is, or when it is `visibility: visible` and its own text has a box. One exception, described below: a box with no size does not hide a node. `aria-hidden` is a separate state, not part of hidden. A child that sets `visibility: visible` under a hidden parent is visible; nothing under `display: none` is. An explicit role is the first recognized token of the `role` attribute; with none recognized, the node keeps its native role. `role="img"` is reported as `image`, and an open `details` is expanded. A closed select lists up to 60 options under it: the ones it offers, so an option that is `hidden`, `display: none`, `aria-hidden`, or inert, or sits under such an optgroup, is left out before the limit counts, as upstream's `isOfferedOption` does (#900). A `visibility: hidden` option stays listed, since a closed select paints none of its options anyway, and a disabled one keeps its state. Each observed element keeps a stable ref for the life of the document, and the engine runs an action on the element that ref names, with no fallback to a text or role lookup in the page. The agent adds the fallback upstream's agent has: a `tap`, `double_tap`, `fill`, `fill_secret`, `press`, `select`, `check`, `uncheck`, or `clear` whose node the engine reports `NODE_STALE` finds the node again by its role, name, and test id in a fresh look and retries, up to twice, scroll and swipe do not retry, and a ref the newest look no longer lists (not one it lists as hidden) is found the same way from the last node it named. A description that matches no node or several fails the verb with `LOCATOR_NOT_FOUND`. Upstream also matches a node's placeholder, input purpose, and container, and forgives a test id that changed; the port matches the three fields it records, and never finds again a node with no name and no test id. Because the port records no container for a node, upstream's `containerKey` fix for windowed lists (`841ea3fa`, a row is not keyed by its list's first rendered row) does not apply. Upstream wraps the retry in `commitTargeted` and the step's accounting; the port has no such wrapper, so each verb runs the loop (`TargetedAsync`) directly, and `ObservationFeed.Relocate` takes the redactor as an argument. Firefox and WebKit launch through `WebEngineOptions.BrowserName`. .NET-only: the first launch in a process runs Playwright's install for the selected browser, and `E2E_SKIP_BROWSER_INSTALL=1` turns it off. .NET-only: `dotnet test` has no flag like upstream's `--headed`, so when `WebEngineOptions.Headless` is unset, `E2E_HEADLESS=0` or `false` shows the window. As upstream, a run is headless by default. As upstream, a headless Chromium run installs with `--only-shell`, a headed Chromium run installs the full build, and Firefox and WebKit install their one build, and the install runs with `PLAYWRIGHT_SKIP_BROWSER_GC=1` unless the user set it. Upstream checks the cache before it spawns the install; the port leaves that to Playwright's install, which does nothing when the build is there. Playwright's .NET `Program.Main` starts the driver with the process environment, so the port sets `PLAYWRIGHT_SKIP_BROWSER_GC` on the process, not on the install alone.

The walk goes through open shadow roots and closed ones that page script attached (an init script records them, as upstream does). Each iframe is a boundary node whatever its role, so an `<iframe role="none">` stays listed with the role `none`, as upstream's walk emits it before any role check, and the engine reads that frame's document through Playwright and puts it under the node, so same-origin and cross-origin frames are both listed and acted on. One observation lists at most 3000 nodes across all frames. When a document has more, nodes that intersect the viewport come first and the rest of the budget goes to the others in document order; the observation reports `Truncated`, and the snapshot tells the model to scroll. A locator resolves against that tree, so matches come in tree order: a match inside a closed root sits where its host is, where upstream lists the light-DOM matches first and the closed root's after them. `OpenAsync` waits for the `load` event.

`WebEngineOptions` carries the upstream `web()` options: `Viewport` (default 1280 by 720, `null` for no emulation), `TestIdAttribute`, `Headers`, `BasicAuth`, `UserAgent`, `Locale`, `TimezoneId`, `ColorScheme`, `ReducedMotion`, `InitScripts`, `Connect` (a CDP endpoint resolver, with an optional `ReconnectEndpoint`), and `Browser` (an `IBrowserProvider`, upstream's `browser: BrowserProvider`). Differences:

- `Headers` ride requests to the base URL's host. Upstream scopes them to the app's site, which can include sibling subdomains
- `Browser` ports upstream's `BrowserProvider` seam (`provider.ts`): `IBrowserProvider` (`Name`, `Scope`, `AcquireAsync`, `ReleaseAsync`, `SweepAsync`), `BrowserProviderScope` (`Worker`, `Attempt`), `BrowserRequest`, `BrowserLease`, and `BrowserReleaseContext`, and the engine side, `LeasedBrowsers`. `BrowserLease.Protocol` (`BrowserProtocol.Cdp`, the default, or `Playwright`) is .NET-only: a `Playwright` lease is dialed with `Chromium.ConnectAsync`, the engine opens its own context with the options it gives a launched one, and it needs `Worker` scope and no `ReconnectEndpoint` because that connection cannot be reattached (a dropped one is replaced by a new lease). A provider is an interface, so upstream's `asBrowserProvider` checks that a method exists have no port; the engine still refuses a blank name, a scope outside the enum, and `Connect` beside `Browser` (`INVALID_CONFIG`). `Scope` and `SweepAsync` are default interface members: a provider that leaves them out leases per worker and sweeps nothing. Neither a request nor a context carries upstream's `signal`: `AcquireAsync`, `ReleaseAsync`, and `SweepAsync` take a `CancellationToken`. `Downloads` (`BrowserProviderDownloads`, with `BrowserDownloadContext`) and `RecordAsync` (`ProviderRecordContext`, `ProviderRecording`, `ProviderRecordingStopContext`, `ProviderRecordingResult`) are default interface members too: a provider with no downloads returns null, and one that cannot record a browser returns null from `RecordAsync`, where upstream leaves the method out. `LeasedBrowsers.Downloads()` and `Recorder()` are upstream's `downloads()` and `recorder()`, and `ProviderRecordings.StopProviderRecordingAsync` is `stopProviderRecording` (`recording.ts`, with `VideoSegment` as `VideoFile` or `VideoLink`). `ProviderRecording.StartedAt` is a `DateTimeOffset`, so upstream's `isProviderRecording` has no port. The engine calls `RecordAsync` through `Recorder` when an attempt records video (see [Video](#video)). `Browser.WaitForDownloadAsync` calls `Downloads` (upstream's `waitForDownload`, with `saveDownloadsTo`, `saveFromBrowser`, and `saveLocally` of `downloads.ts` as `Downloads.SaveDownloadsToAsync`, `SaveFromBrowserAsync`, and `SaveLocallyAsync`). A provider's directory is checked at config load too
- A runner calls `WebEngine.PrepareAsync`, `Init`, `FinishAsync`, and `DisposeAsync` as upstream's `prepare`, `init`, `finish`, and `dispose`, with `EnginePrepareInfo`, `EnginePrepareResult`, `EngineInitInfo`, and `EngineFinishInfo`; an attempt is `StartAsync` and the dispose of its session (`startAttempt` and `endAttempt`). The hand-off to a worker travels in the same `E2E_WEB_BROWSERS_<TARGET>_<DIGEST>` environment variable, capped at 16384 bytes. Upstream's web `locate` (`surface.ts`) projects the expression onto Playwright selectors (`locators.ts`), which the port's page script replaces; the port resolves over the tree it already reads, so only the `selector` and `frame` expression kinds ask Playwright (see the `Browser.Locator` bullet below). The web engine reads under the `timeout` it is given (what is left of the wait, at least 500 ms), or the action timeout when that is shorter; the document engine answers at once and does not use it. `LocatorExpression.IncludeHidden` is .NET-only: `toBeAttached` and `waitFor` set it so an engine that resolves over its tree matches hidden role nodes, which they matched before the engine located; upstream's Playwright has no such switch. A locate hands the trace the observation it read (`TraceFeed.ShowScreen`, and `EngineStartOptions.Screen` on the document engine), as core's `Agent.ObserveAsync` did for the resolve it replaces; upstream's web `locate` shows none. A retryable `EngineException` of the read (`NODE_STALE` during a navigation) is now retried until the wait's deadline, as `resolveOnce` does. Any session that says no `CanLocate` (the WinApp engine, a scripted engine) has its locator resolved over `ObserveAsync` in core, as before. `Screen.GetByTestId` on such an engine, and the `LocatorResolver` readers of screenshot masks and `e2e mcp`, still resolve over the observation.
- A web node that `LocateAsync` returned as the only match of its locator stays strict, as upstream's `locate` (`surface.ts`, #859) keeps the strict Playwright locator for a single match: `PerformAsync` resolves the same locator again and, when a second element now matches, throws a retryable `NODE_STALE` (`Node <ref> now matches more than one element. Observe again.`) before any input, so the action acts on neither. Upstream gets this from Playwright's strict mode; the port's refs are page-script ids, so `WebEngine` keeps the locator of each single-match node (`_strict`, .NET-only, keyed by the node instance a locate returned) and re-resolves it in `RequireNoNewTwinAsync`. A node the observation listed (it has the same ref), a node among several matches, and every match of a display-value or exact-label query (upstream pins those to the element handles it read) name their own element and are never stale for a twin. Differences: upstream counts the elements of the whole projected locator (`reads.length`) and the port the nodes its resolver returns; and the port has no web `dragTo`, so upstream's drag case of #859 (ACTION_MAY_HAVE_COMMITTED when a drop target turns ambiguous after the press) has no port.
- `Browser.Locator(selector)` and `Browser.FrameLocator(selector)` are upstream's `browser.locator` and `browser.frameLocator` (`browser.ts`). `FrameScreen` is upstream's `FrameScreen`: a `Screen` (so `Screen` is no longer sealed, though only the port can derive from it) whose every query goes through a `frame` expression, with `Locator(selector)` and `FrameLocator(selector)` for a CSS or XPath selector and a nested frame. A locator of a frame screen can `Or`, `Filter`, and scope as any locator, since `Screen.OwnLocator` compares the attempt's root screen (upstream compares the context). `LocatorExpression` has the `selector` kind (the device's, now the web engine's too) and the `frame` kind (`Selector` is the iframe's selector, `Source` the scoped expression). `WebEngine.LocateAsync` resolves them in `WebSession.ProjectAsync`, over the tree: Playwright says which elements a selector, or an iframe, names (`WebLocators` is upstream's `locators.ts`, with `FrameSelectors`), the elements' refs go to the resolver as a `refs` expression (`LocatorExpression.Refs`, .NET-only, internal), and a frame scopes its queries to the iframe node's descendants, where the walk hangs the frame's document. Differences: an element the tree leaves out (no role, test id, or text of its own) matches nothing, where upstream's Playwright locator matches any element; an iframe the page does not show has no node, so it is `FRAME_NOT_FOUND` (retryable) and its content is not reachable; a read that does not wait (`Count`, `AllAsync`, `AllTextContentsAsync`, `IsVisible`, `IsHidden`, `toBeAttached`, `toBeVisible`, `toBeHidden`, `toHaveCount`, a text list, and `WaitFor` for `Detached` or `Hidden`) answers no match for a missing frame (`MissingFrame.Empty`, upstream's `missingFrame: 'empty'`), and any other resolve polls for it until its timeout and fails with `NOT_FOUND` (`FRAME_NOT_FOUND`) or `STRICT_MODE` (`FRAME_AMBIGUOUS`), as upstream's `translateLocatorError` maps them to `LOCATOR_NOT_FOUND` and `LOCATOR_AMBIGUOUS`. A `Filter(has)` resolves inside each match, so a frame its locator shares with the source is the source's; a `has` from another frame fails with `UNSUPPORTED_CAPABILITY`. A frame selector must match an `iframe` or `frame` element, else the frame is missing. A selector that captures with `*` before its last part fails with `INVALID_LOCATOR` when the locator resolves; upstream finds out when its read selector returns nothing for the captured element, the port reads the spelling (`WebLocators.RefuseCapture`, which splits on `>>` outside quotes), and its message says `Filter(Locator)` where upstream says `filter({ has })`.
- `BrowserExpect.ToHaveClassAsync(locator, expected)` is upstream's `expect(browser).toHaveClass`, on `Expect.That(browser)` and `Expect.Soft(browser)`. A string is the whole class list, whitespace-normalized, and a `Regex` is tested against it. A locator with no match yet keeps it polling (`observed: no node`), a node with no `class` attribute fails it (`observed: no class attribute`; `class=""` is an empty list), and several matches fail it at once with `STRICT_MODE` (upstream's `LOCATOR_AMBIGUOUS`). The step's label is `page`, as the other `expect(browser)` matchers' here, where upstream's is the expected pattern.
- `IEngineSession.StartVideoAsync` and `StopVideoAsync` are upstream's `artifacts.startVideo` and `artifacts.stopVideo`, and `EngineCapabilities.Video` is its `video` artifact capability. `EngineStartOptions.ArtifactsDir` is `EngineAttemptContext.artifactsDir`: the attempt's `.e2e/results/<result>/attempt-<n>`. `WebEngine` starts the video once the attempt's page is open, and `WebSession` (upstream's `AttemptSession`) tells it when pages open and close.
- `VideoRecorder` and `ProviderVideo` implement `IAttemptVideo` (internal), upstream's `AttemptVideo`. `VideoRecorder` writes `video/video.webm` and, for later pages, `video/video-part<n>.webm`, each with its `StartedAt`, from Playwright's `IPage.Screencast.StartAsync`. `ProviderVideo` returns the one segment the provider made: a file it wrote under `video/` (Kernel's `replay.mp4`) or a `VideoLink`. The first-frame wait is the same `FirstFrameWait` (1 s). `WebScreencastOptions` (`WebEngineOptions.Screencast`) is upstream's `WebScreencastOptions`; `Size` is a `WebViewport` and a size under 1 pixel or a `Quality` outside 0 to 100 is `INVALID_CONFIG`. The old `web({ video })` key has no port, since the options are typed.
- A browser provider that records is asked through `LeasedBrowsers.Recorder`. Upstream leaves `record` out of a provider that cannot record, and the engine then records the screencast. A .NET provider is an interface, so it returns null from `RecordAsync` and `ProviderVideo.IsRecording` is false: the session then arms a `VideoRecorder` instead. A page the app closes under a `ProviderVideo` needs nothing, as upstream.

A required video that cannot be finalized makes `DisposeAsync` throw. The kept segments are `E2ESession.Videos` (internal); the port has no report to register them in.
- `App.StartRecordingAsync` / `StopRecordingAsync` are upstream's `app.startRecording` / `app.stopRecording` (#1381), with `RecordingOptions`, `RecordedVideo`, `RecordedVideoFile`, and `RecordedVideoLink` (a class hierarchy where upstream has a union; `StopRecordingAsync` returns an `IReadOnlyList` that is never empty, where upstream types a non-empty tuple). `Recordings.cs` is `run/recordings.ts`: `SessionRecordings` shares the engine's one recorder between the attempt's video and the spans (`Recordings.SessionRecordings` is `sessionRecordings`; the extra `recordsVideo` argument is .NET-only, since the port's session always has `StartVideoAsync` and the engine declares `EngineCapabilities.Video`). The App methods take a cancellation token, not upstream's action-timeout bound, as `ScreenshotAsync`. Not ported: the `run_code` surface entries (`mcp/code-surface.ts`; the port has no `run_code`), and the serial-group stop of a member's recording (the port has no serial groups). Tests: `AppRecording/` (`AppRecordingsTests`, all seven `it` of `tests/unit/app-recording.test.ts`; `AppRecordingsRunTests`, the four of `tests/integration/app-recording.test.ts`, partial: one session each, no runner), `Video/VideoRecorderTests` and `E2E.Mobile.Tests/Engine/VideoTests` (the added re-record `it`s), and `ReportFailureText/RenderTracePageTests` (the recording-span offsets).

## Trace feed

What the trace page shows about the app is collected as upstream's `trace-feed.ts` collects it, and kept on the attempt's step records. The page that reads it is described in [Trace page](#trace-page).

- `EngineStartOptions.Screen` and `EngineStartOptions.Environment` are upstream's `EngineAttemptContext.screen` and `environment`. `TraceFeed` (`Engine/TraceFeed.cs`, internal) is upstream's class: after an action, `ScreenAfterActionAsync` captures the screen like an observation without publishing it, so the refs a test or the model holds stay valid, within one second; `TellEnvironment` tells the browser (`chromium 141.0`) and the page's user agent once an attempt, without anyone waiting for it. The web engine builds the feed when the attempt starts. It hands the screen after `OpenAsync`, `BackAsync`, `PerformAsync`, `PressAsync`, and `SwipeAsync` (upstream's `open`, `back`, `perform`, `pressKey`, and the viewport swipe), and tells the environment after `OpenAsync` and `BackAsync` (upstream's `navigating`). Upstream's `typeText` and the point actions have no engine member here.
- An attempt that keeps a trace (the same keep rule as the video: `attemptKeep` of the resolved `trace` mode) hands the engine a `Screen` sink. An attempt that keeps none hands none, and takes no screen from what the test observes. The default mode, `retain-on-failure`, keeps one for every attempt, since the verdict is not known before the end.
- `SessionScreens` (`Run/SessionScreens.cs`) is upstream's `screens` of `TargetSession` and `EnvironmentFacts` is its `createEnvironmentFacts`: a name told again overwrites, blank values are dropped, at most 8 facts, each redacted and then cut to 40 and 200 characters. The port has no `createEngineSession`, so they are classes of their own. `AttemptScope.ObserveAsync` shows each observation the test, the screen fixture, and the agent take to the same sink.
- `StepRecorder.RecordScreen` and `StepScreens.CompareScreens` and `TraceScreen` (`Run/StepScreens.cs`) are upstream's `recordScreen` and `step-screens.ts`. A step keeps how the last screen it saw differs from the step before's (`StepRecord.Screen`): the node lines added, removed, or changed, without node ids, 12 at most. Differences: the engine hands the port a typed `Observation`, so `SessionScreens` has no check for a malformed snapshot or `treeUnavailable`, and no revision to mint. The screen's location is the route (`/todos`), not the whole URL, and a node that is hidden or `aria-hidden` is left out, as the lines the model reads leave it out. The byte budget is the run's `maxObservationBytes`, the largest any agent allows (262144 by default), as upstream's `config.limits.maxObservationBytes`.
- `E2ESession.Steps`, `E2ESession.Environment`, and `E2ESession.AppLog` (internal) hold what the page reads.
- The app log is collected apart from the feed, as upstream does it. `EngineStartOptions.AppLog` and `EngineStartOptions.Navigation` are upstream's `EngineAttemptContext.appLog` and `navigation`, and `AppLogEntry` is its `AppLogEntry`; `AppLogSource` and `AppLogLevel`, the records' enums, are public for it. `AppLog.Install` and `NavigationLog` (`Engine/AppLog.cs`, internal) are `installAppLog` and `NavigationLog` of `web/src/app-log.ts`. On every context the web engine configures, a persistent one too, it reports console output (`error` and `assert` as errors, `warning`, `log` and `info` as info; `debug` and the rest are left out, and so is Chrome's `Failed to load resource:` echo, which the network lines tell), uncaught errors, failed requests (one the browser cancelled is left out), and responses with a status of 400 or more (5xx an error, 4xx a warning, a missing `/favicon.ico` left out). It tells where the page went: `navigated to /checkout`, `the new tab navigated to /help`, `frame "pay" loaded /embed`, and `the app opened a new tab at /help; the test stays on its page`. A navigation the engine makes itself is not told, since its step says it: `NavigatingAsync` (upstream's `navigating`) wraps `OpenAsync` and `BackAsync`, and also `ForwardAsync`, `ReloadAsync`, and `GotoAsync`, as upstream wraps `browser.goto`, `reload`, `back`, and `forward`. It also tells the environment, as upstream's `navigating` does. Differences: the console location is Playwright's `URL:line:column` string, read to `(at URL:line)`, and an uncaught error is the text Playwright gives (the message, then the first `at` frame), where upstream reads the error's name, message, and stack.
- As upstream, a tab's first document is told by its opening, a page that is not the test's current page counts as a tab (so the test page's navigation while `RestartAsync` replaces it reads as a tab's), and a request a test aborts itself (`net::ERR_FAILED`, `ERR_BLOCKED_BY_CLIENT`) is logged: only the browser's own cancellations are left out.
- .NET-only names: `StepHooks`, `E2ESession.Phase` and `E2ESession.AppLog` (internal), `StepEvents` (the step's events, safe to read while the engine appends), and `AppLog`, `NavigationLog`, and `AppLogRoute` as the homes of upstream's `installAppLog`, `NavigationLog`, and `AppLogRoute`. .NET-only tests: `StepHooks/StepHooksTests` in `E2E.Tests` and `E2E.NUnit.Tests`. `EngineStartOptions.AppLog` and `Navigation` are for engine authors, as `Screen` and `Environment` are; no user guide describes the engine contract, so the guides tell only what the trace page shows.
- `AppLogRoute` (`Run/AppLogRoute.cs`) is upstream's `AppLogRoute` of `TargetSession`, built by `createAppLogRoute` (`engine/session.ts`), and `AppEvent` and `AppLogLimits` are its `AppEvent` and `APP_LOG_LIMITS`. The engine reports from the moment it starts, before any step records, so what arrives before the recorder takes it waits: errors and warnings up to 200, info up to 100, navigations up to 50, so chatter never crowds out an error. An entry with a source or a level outside the enums, or a blank text, is dropped. The route is a class of its own, since the port has no `createEngineSession`. `StepRecorder.RecordAppEvent` and `AppLog()` are upstream's `recordAppEvent` and `appLog()`: a line goes to the attempt's app log with the step running in this async context, else the step that started last, redacted and then cut to 300 characters; where the app went is a `navigation` event of that step, and one before the first step is told under it.
- Step events, #443. A locator action records an `engine` event, upstream's `recordAction` of the locator engine: the action, the node it landed on as the resolve read it (role and label, secrets redacted), and `appeared after Nms` when the node took more than one round to appear. An action that failed records its code. The port retries no stale node, so an event never says `went stale`; `PressSequentiallyAsync` is one `pressSequentially` event where upstream focuses first and records `focus`; the action `selectOption` is named `select`, as the engine contract names it. `RecordedTarget.TargetLabel` is upstream's `targetLabel` (`cache/trace.ts`). An assertion on a locator and `WaitForAsync` record a `poll` event with the count of reads and, when the reading changed or the poll failed, the readings in order: `SampleHistory` (`Expect/SampleHistory.cs`) is upstream's class (`expect/samples.ts`), `RecordAsync` its `record`. An agent step records the events upstream's `instrumentPhase` records (`Phases.InstrumentPhaseAsync`, `agent/phases.ts`; `PhaseHost`, `PhaseSpec`, and `PhaseDetail` for its `host`, `spec`, and `detail`; `PhaseDetail` is .NET-only, since upstream's is a `Partial<StepEvent>`; the port's `PhaseSpec` has no `api`, which upstream never reads). Every look the step takes is an `observation` event with the nodes it read and its size in bytes, as a model reads it, and a look taken inside an action is named: `relocate` for the fresh look that re-finds a stale node, `page` for the look between the pages of a scroll. A judgment records one `observation` event for its look. Differences: the port's action body commits and notifies inside the phase (the action is recorded and the test's `OnAction` hook has run when the event ends), where upstream's phase ends before it, so an `engine` event also holds the settle look and the hook; the `model` events are recorded where each model call is counted (`AddModelCall`), so the model phase announces no activity; and there is no `agent.cache` phase or `policy` event.
- Agent step events, #648. `Observation.Revision` (public, set by the harness; upstream's `Observation.revision`) is `b<n>` for the attempt's n-th capture through `AttemptScope.ObserveAsync`, so an observation an engine hands a locator directly has none. Between judgments the wait maps that timeout onto `waitFor timed out; last judgment: ...` with the step's timeout as the cause, as upstream's `waitForNextJudgment` does; the first capture, before any judgment, keeps the bare message. Tests: `AgentPhases/InstrumentPhaseTests`, `RetryingObserveTests` and `CheckStepClockTests` port the three `describe` blocks of `agent-phases.test.ts`; `foreignEngineError` (an engine from another module registry) has no .NET counterpart, so those tests throw the engine's own `EngineException`. - The hook a step ran in, #443. `StepRecorder.Phase` is upstream's `phase`, and `E2ESession.Phase` (internal) its `enter`. Upstream's runner enters `beforeEach` and `afterEach` itself. ## Trace page

Upstream's `--trace` writes `<output>/results/<result>/trace.md`, a markdown page that tells the whole attempt: what failed and where to look, every step with what it did, the cache's decisions, what the app logged, the agent's last turns, the screen at failure, and what the attempt ran on. You open the file; there is no viewer. A test run has no `--trace` flag, so `trace` and the .NET-only variable `E2E_TRACE` choose which attempts keep a page (see [Config](#config)); the default is `retain-on-failure`. `e2e explore --trace [mode]` is the flag itself.

- A session writes the page when it is released, after the video is stopped, the engine is closed, and the debug table and the AI trace are written, and before a required video's failure is rethrown. It writes when an attempt of the test kept a trace, by `attemptKeep` and `keeps` (the rule the video follows), and the page then tells every attempt, see below. A page that cannot be written prints a line on stderr and never hides the test's result. The page goes in the test's directory under the results directory, `.e2e/results/<result>/trace.md`, beside the `attempt-<n>` directories, as upstream's does. A session is one attempt, and each adds itself to `RunReport` (.NET-only, `Report/RunReport.cs`), which collects the attempts of a test: a first attempt starts the test over, a later one extends it. The page tells every attempt the test has had so far, as upstream's does from the run report, and is written when any of them kept a trace (upstream's `tracedResultIds`). So a flaky test reads `Passed after 1 failed attempt` with the last failure, and a test that failed every attempt reads `Failed the same way on both attempts`, even when the passing or last attempt kept none itself. The run keeps the attempts of a test only while it has not passed and the mode is not `off`: an attempt that passed or was skipped ends the test and drops them. The port cannot know the last attempt of a test that keeps failing, since the adapters do not tell the session the retry count, so those entries stay until the process exits. Upstream's runner holds every result of the run in memory too (`const results: ResultRecord[] = []` in `run/runner.ts`), for its report.
- The MCP server's sessions set `trace` to `off`, so they write no page and take no screens: an MCP session is for looking, and `e2e mcp` has no `--trace`, as upstream. An exploration takes the target's mode, or `--trace`; its own verdict gets no page.
- `TracePages.WriteTracePagesAsync` and `TracePages.TracePage` are upstream's `writeTracePages` and `TRACE_PAGE` (`report/traces.ts`). `FailureText.RenderTracePage`, `ToldAttempt`, `FailedStepOf`, `AttemptsLine`, `FailureSource`, `EvidenceOf`, `DetailLines`, and `StepLabel` are the matching functions of `report/failure-text.ts`, and `MarkdownText` and `ReportFormat` are `report/markdown-text.ts` and the parts of `report/format.ts` the page uses. `ArtifactPaths.ResultSegment` is `resultSegment` (`run/artifacts.ts`; it also strips a `.cs` extension). All are internal.
- `Report1Document`, `ReportRun`, `ReportResult`, `ReportAttempt`, `ReportError`, `ReportArtifact`, `FailureEvidence`, and `Outcome` (`Report/ReportRecords.cs`) are the part of upstream's report the page reads, and `AttemptReport.Build` (`Run/AttemptReport.cs`, .NET-only) fills them from the step recorder, the environment facts, and the video segments of one attempt. `ReportAttempt` is upstream's `ReportAttempt` and `AttemptView` in one, since the port has no serial groups. The file is the first step's file (`unknown` without a step), the run id is one per process, and the title is the test's title as one part. `RunReport.Add` joins an attempt to its test's result and derives the result's status from the attempts (`Flaky` when the final attempt passed after one that did not), where upstream's runner keeps the result record and `buildReport` reads it.

## Report document

Upstream writes `report.json`, a `report-1` document of the whole run (`report/build.ts`), checked by `schema/report-v1.schema.json`. The port writes it too (#496), with the differences below.

- **When and where.** Upstream builds the document once, when its runner ends the run, and writes it to `<output>/report.json`. A test framework runs the port's attempts as sessions with no run around them, so each session adds its attempt to the process's run (`ReportFile.WriteAsync`, .NET-only) and the whole document is written again, atomically, to `report.json` beside the results directory (`.e2e/report.json` by default, as `ai-trace.json` is). The file is complete after every attempt. `run.finishedAt` and `run.status` are those of the attempts so far, not final, and `run.exitCode` is the worst exit code of the results, as upstream's `verdictExitCodes` derives it: a failed or timed-out result exits 1, or 2, 3, or 4 when the category of an attempt error is `configuration`, `infrastructure`, or `internal` (an agent code's category comes from `AgentError.CategoryByCode`, upstream's `CATEGORY_BY_CODE`, so a blocked `AUTH_CREDENTIAL_UNAVAILABLE` exits 2), and an interruption exits 130, which outweighs the rest. An attempt whose `cleanup` is `failed` adds the categories of its `cleanup`-phase secondary errors (`ReportRecords.CleanupErrorsOf`, upstream's `cleanupErrorsOf`, tester-army/e2e#1233), so a passed or skipped test whose cleanup failed exits 3 (a session marks its attempt's cleanup failed, with a `cleanup`-phase secondary error, when the engine session does not close or a required video is not finalized, as upstream's `closeSession` does, and the test's own verdict stays; `DisposeAsync` still throws the failure, unless the session's own commit failure is thrown instead (the report holds both); a best-effort video that fails is not a cleanup failure; the port has no list reporter, so the `cleanup failed` line and the `Cleanup` summary row have no port). `run.status` follows the code (`passed`, `failed`, `interrupted`, else `error`), and `blocked` is derived from the results afterwards. A result keeps its wire form until it gains an attempt, so a large suite does not serialize every result again after each attempt. A result id is the test's file and title, so a test that runs twice in one process (another target, a repeat) is one result that its last run replaces, as `RunReport` already treats it. Test processes that share an output directory overwrite one another's file, and a file from an earlier run is replaced by the first attempt. It is written whatever the `trace` mode, for passing tests too. A write that fails (disk, permission) prints one line to stderr and does not fail the test.
- **A retry the run interrupted** (`retryVerdict`, `run/retry.ts`). `Retry.RetryVerdict` (`Run/Retry.cs`) is upstream's `retryVerdict`, and `RetryAttempt` is its type of that name. `RunReport.StatusOf` (.NET-only, it collects the attempts of a test) derives a result's status from it: a pass after an attempt is `flaky`, a skip decides, and an interrupt during a retry keeps the failed or timed-out verdict before it, so `Outcome.Verdict` (upstream's `outcome().verdict`) picks the attempt that failed and not the interrupted retry. An interrupt of the first attempt is `interrupted`, and no attempts read as `failed`, as upstream does. The run-level interrupt flag is `RunState.Interrupted` in `ReportFile` (.NET-only, it is the process's run), where upstream's runner keeps `interruptController` (`run/runner.ts`): it is set when a session adds an attempt that a user cancel ended (`AttemptStatus.Interrupted`; a test timeout is `timed-out`, not an interrupt). `E2ESession.Complete` takes the user's cancel from the caller's `cancellationToken` (the runner's token that the xUnit and NUnit adapters pass): an `OperationCanceledException` with it not cancelled (an HTTP timeout in the test) is a failure, or a timeout when the session's own `TestTimeout` fired (its error is recorded as `TEST_FAILED` or `TEST_TIMEOUT` wrapping the cancellation, since a `CANCELLED` error would read as the interrupt category and exit 130), and a failure is never upgraded to an interrupt, so a timeout a framework reports as a failure stays one. The flag is read from the results the run holds (a rerun that replaces an interrupted result clears it; the retries of a test stay in its result), and `ReportFile.StatusOf(results, interrupted)` adds 130 to the verdict exit codes when it is set, as upstream's `currentExitCode` does. So a run whose retry was interrupted after a failure reads `interrupted` with exit code 130 in `report.json`, while that test keeps its `failed` verdict. The xUnit adapter's `ErrorForCache` (.NET-only) hands a test that xUnit recorded as failed with an `OperationCanceledException` or `TaskCanceledException` to the session as an `OperationCanceledException` (xUnit keeps only the type name and message), so the session tells the user's cancel by the runner's token as it does for any test; the NUnit adapter already passes the recorded exception. Known gaps ([#837](https://github.com/hardkoded/e2e-dotnet/issues/837)): the flag is derived from attempts, where upstream's comes from the interrupt signal itself, so a cancelled signal that ends no attempt (a session that never starts) sets nothing; `Report()` (`ReportFile.SingleAsync`, .NET-only: it is the report of one session, a run of one result, as upstream's `writeHostTrace` builds it) applies the flag to its own result only, since it sees no other result of the process. Upstream drops the 130 when the run stopped itself (`runAborted`, `stoppedEarly`); the port has no scheduler or run-level errors, so it has neither. A string is compared after both sides go through `System.Uri` (not WHATWG), which agrees with Chromium on the default port, the trailing slash, dot segments, and percent-encoding. But a tab or newline inside a URL is escaped, not stripped, so `view-\tsource:file:` opens as an http path under the base URL (or fails with `APP_URL_REQUIRED` without one) instead of `POLICY_DENIED`. A percent-encoded unreserved character in the path is decoded (`%66ile:` becomes `file:`). Neither opens a scheme other than http(s).

`DocumentEngine` supports `app.back` (it rebuilds the previous route), `app.restart`, and `app.clearState` (both drop the history and reopen the base URL). It has no viewport: `DocumentPage.OnScroll` and `DocumentElement.OnScroll` let a page load more rows when it is scrolled. It has no browser, so every `Browser` member fails with `UNSUPPORTED_CAPABILITY`. A custom engine opts in by implementing `IBrowserSession`, and by overriding the default `BackAsync`, `RestartAsync`, and `ClearStateAsync` on `IEngineSession`, which otherwise fail with `UNSUPPORTED_CAPABILITY`.

## Models

Upstream takes any AI SDK model instance. JSON cannot hold one, so `agents.<name>.provider` names the client, and code builds one with `ModelProviders`, `Subscriptions`, or a client's options. Each client speaks its vendor's wire protocol directly:

| Upstream | `provider` | .NET |
| --- | --- | --- |
| `@ai-sdk/openai` chat, `@ai-sdk/openai-compatible`, Ollama | `openai`, `openai-compatible` | `OpenAiCompatibleModel` |
| `@ai-sdk/openai` Responses, `@ai-sdk/azure` | `openai-responses`, `azure` | `OpenAiResponsesModel` (`ModelProviders.AzureOpenAi`) |
| `@ai-sdk/anthropic` | `anthropic` | `AnthropicModel` |
| `@ai-sdk/google` | `google` | `GoogleModel` |
| `@ai-sdk/amazon-bedrock` | `bedrock` | `BedrockModel`, signed with SigV4 or a Bedrock API key |
| `@ai-sdk/xai` | `xai` | `OpenAiCompatibleModel` at `api.x.ai` |
| `@openrouter/ai-sdk-provider` | `openrouter` | `OpenAiCompatibleModel` at `openrouter.ai` |
| `gateway()` from `ai` | `gateway` | `OpenAiCompatibleModel` at `ai-gateway.vercel.sh` |
| `chatgpt()` | `chatgpt` | `Subscriptions.ChatGpt` |
| `copilot()` | `copilot` | `Subscriptions.Copilot` (`CopilotModel`) |
| `grok()` | `grok` | `Subscriptions.Grok` |
| `opencodeConsole()` | `opencode-console` | `Subscriptions.OpenCodeConsole` (`OpenCodeConsoleModel`) |

Keys come from the environment variable the AI SDK reads (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `AZURE_API_KEY`, `XAI_API_KEY`, `OPENROUTER_API_KEY`, `AI_GATEWAY_API_KEY`, `AWS_*`), or the one `apiKeyEnv` names.

Subscriptions follow upstream: the same four logins (`openai` PKCE on port 1455 or `--device`, `github-copilot` from `gh` or an OAuth App's device flow with enterprise hosts, `opencode-console` and `spacexai` device flows), the same credentials file (`$XDG_CONFIG_HOME/e2e/oauth.json`, mode 0600, locked and replaced atomically, unknown entries kept), `E2E_OAUTH_CREDENTIALS`, refresh two minutes ahead of expiry with one refresh shared per file (a cancelled call stops waiting for it, and the refresh finishes for the others), a retry after a 401, Copilot's chat-or-Responses choice from the plan's listing, OpenCode Console's per-model protocol from the workspace config, and `OPENCODE_API_KEY`, which replaces the login for the model and for `e2e models opencode-console`; bare `e2e models` also lists OpenCode Console when only the key is set, and a missing login's message names the key. The OpenCode Console model always asks the Anthropic route for 8192 output tokens, as upstream does when a call sets no cap. A missing or rejected login fails the step with `MODEL_PROVIDER_FAILED`, blocked, naming the `OAuthException` code (`NOT_LOGGED_IN`, `LOGIN_REQUIRED`). Tests: `oauth/errors.test.ts` is `OauthErrors/` (`DescribeResponseTests`: both `it` of `describeResponse`; `ReadJsonBodyTests`: the `it` of `readJsonBody`, which is `TokenEndpoint.ReadJsonBodyAsync`) and `oauth/token-endpoint.test.ts` is `OauthTokenEndpoint/RequestTokensTests` (all 3 `it`).

Differences:

- Requests are not streamed. The Codex backend only streams, so its event stream is folded back into the final response, as upstream folds it
- The Vercel AI Gateway and OpenRouter are reached over their OpenAI-compatible chat API, so a gateway model gets no Anthropic cache breakpoints or OpenAI cache key. The gateway reads `VERCEL_OIDC_TOKEN` from the environment but does not run `vercel env pull` itself
- Gemini tool schemas go as `parametersJsonSchema`, unconverted, and the judgment schema as `responseJsonSchema`, as the AI SDK does: `@ai-sdk/google` 4.0.105 (the version upstream locks) sends `parametersJsonSchema: tool.inputSchema` and no longer runs `convertJSONSchemaToOpenAPISchema` (vercel/ai #20757, "preserve JSON Schema instead of converting to OpenAPI schema"). For `responseJsonSchema` it only rewrites `const` to a one-value `enum` (`sanitizeResponseJsonSchema`); the port's tool, `explore`, and judgment schemas use no `const`, so there is nothing to rewrite. Gemini's docs list only some JSON Schema keywords; the port's schemas also use unlisted ones such as `maxLength`, which were not verified against a live Gemini call. Gemini 3 thought signatures are kept per model instance and sent back with their function calls
- A Responses model (OpenAI, Azure, and the subscription backends) replays its reasoning on the next turn as upstream does: nothing is stored, so the request asks for `reasoning.encrypted_content` and sends each encrypted reasoning item back inline, ahead of the turn's text and tool calls (all reasoning items first, not interleaved as returned). The request asks for it from every model except those named `gpt-3*`, `gpt-4*`, `chatgpt-4o*`, and `gpt-5-chat*`, as the AI SDK does. Anthropic replays its thinking blocks, signature and redacted data included, ahead of the turn's text and tool calls, and chat completions replay `reasoning_content` (read from `reasoning_content` or `reasoning`) on the assistant message, as the AI SDK does. Google replays its thought parts (`thought: true`, with their `thoughtSignature`) and Bedrock its `reasoningContent` blocks (`reasoningText` with its signature, or the redacted content) the same way, ahead of the turn's text and tool calls. A Gemini text part with a `thoughtSignature` and no `thought: true` keeps its signature and sends it back on that same text part on the next turn. A Bedrock request is signed again for every attempt (`ModelHttp.SendAsync` takes a `sign` callback), as the AI SDK signs inside each fetch, so a retry after a long wait carries a fresh `x-amz-date`
- On Anthropic, the tool loop stops replaying the thinking from a message it rewrote since the last request (an executor's `PrepareMessages` changed it, or the history was shrunk after a context overflow) on, as upstream does, since Anthropic binds each thinking block to the prefix before it. The loop compares each message by value with what the last request sent (`MessageShape`), drops the reasoning with `ProviderHints.AfterEdit` (upstream's `afterEdit`, taking the model, since the port has no `providerHints(model)` factory; its `SpeaksAnthropic` check reads the model object where upstream's reads a provider and model id), and notes it on the turn. The drop is permanent for the step, and reasoning produced after the rewrite stays. Only `AnthropicModel` and such a `BedrockModel` do this: a Bedrock model whose id names Anthropic behind an optional region prefix (`eu.anthropic.claude-…`) does it too, as upstream's `speaksAnthropic` recognizes it (the id is read off the `BedrockModel`; a Bedrock application inference profile ARN is not recognized, as upstream). The port has no Vertex or OpenRouter client that replays Anthropic thinking, and it has no per-turn elision of superseded screens, so those two rewrites are the only ones. The part of the change that keeps the system prompt fixed across a switch to `auto` has nothing to do here, since the port sends `tool_choice: auto` from the first turn
- `azure` uses the Responses API at `/openai/v1` with `api-version=v1`, as the AI SDK's `azure()` does. Bedrock signs with `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (and `AWS_SESSION_TOKEN`) when both are set and otherwise resolves the AWS credential chain (shared profile via `AWS_PROFILE` or the default profile, SSO, container and instance roles) with the AWS SDK for .NET (`AWSSDK.Core`), as the AI SDK's amazon-bedrock provider does with the AWS SDK for JavaScript. Upstream has no symbol for it, since the AI SDK owns the chain, so `AwsCredentialChain` and `BedrockModelOptions.CredentialChain` (internal, a test seam) are .NET-only. A chain that finds nothing ends the step with `MODEL_PROVIDER_FAILED`; the chain's own message is redacted
- A model request the provider refuses as too large ends with `CONTEXT_OVERFLOW`, blocked, and names the same status and body. The port uses upstream's patterns for the refusal (every provider's wording, any HTTP 413, a throttling text vetoed) on the message and the body. As upstream does, `agent.act` then shrinks the step's history once and sends the request again: every superseded screen is elided, and any text past 16,384 characters is cut to its head with a notice. The refused request spends no model call, and the retry runs through the turn's preparation again, so an executor's `PrepareMessages` sees the shrunk history, as upstream's `prepareMessages` does. A second refusal, or a first one with nothing to shrink, ends the step and says which. The port has no screenshots and no earlier budget for stale screens, so a screen is elided only at a refusal.
- A model that refuses a request (finish reason `content-filter`) ends the step with `MODEL_REFUSED` instead of `MODEL_PROVIDER_FAILED`, as upstream does, and the step cache reads it as a failed flow like `MODEL_OUTPUT_INVALID`. The port has no AI SDK to map each provider's stop word, so its providers do: `refusal` (Anthropic), `content_filter` (chat completions, and Responses `incomplete_details`), `SAFETY`, `RECITATION`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, and `IMAGE_SAFETY` (Gemini, and a prompt it blocks with no candidate, by `promptFeedback.blockReason`), `guardrail_intervened` and `content_filtered` (Bedrock). A refused turn that still called a tool is kept, as upstream keeps a usable answer. The message names the model without a provider, because an `IAgentModel` has only a name, and quotes the provider's word redacted and cut at 128 characters
- A model GitHub Copilot does not serve to the account (`model_not_supported`, a 4xx answer) ends the step with `MODEL_UNAVAILABLE`, blocked, naming the model and the causes (the plan, the Copilot settings, an unknown id), as upstream's `copilot()` does. Upstream also marks the failure so its runner reports it once and stops the run; the port has no run-level error list and no workers, so every step that calls the model fails the same way. A model on the wrong endpoint (`unsupported_api_for_model`) stays a `MODEL_PROVIDER_FAILED`
- A model request answered with an error status ends with `MODEL_PROVIDER_FAILED` and names the HTTP status and the response body, secrets redacted, cut at 1 KB. The port never parses a provider's error body, so it quotes every one. Before it fails, the request is sent again up to 5 times (upstream's `TRANSPORT_RETRIES`, `ModelHttp.TransportRetries`) after a network failure or a status the AI SDK treats as retryable (408, 409, 429, and every 5xx), waiting the provider's `retry-after-ms` or `retry-after` when it is under a minute (or under the backoff) and otherwise 2 seconds doubled each time; the failure is the last attempt's. A request that got no response in 120 seconds is not sent again, and the step's deadline or a cancel ends the wait. The port has no forced `tool_choice` to retry with `auto`: every request already sends `auto`
- Every model request sends upstream's identity headers, replacing the same headers set on the client, but names this port so its traffic is not counted as upstream's: `User-Agent: e2e-dotnet/<version> (<platform>; <arch>)` (the NuGet version; the platform and arch by Node's names), `HTTP-Referer: https://github.com/hardkoded/e2e-dotnet`, and `X-Title: e2e-dotnet`. Model requests append `runtime/dotnet/<version>` after it, where upstream has the AI SDK's user agent. Login requests send the same user agent, as upstream's do, and still name the `e2e` originator and referrer that upstream registered
- `e2e login` with no provider shows a numbered list instead of upstream's picker. `e2e models` prints the same columns. `e2e login` prints the sign-in URL on a line of its own, as upstream does, with plain lines where upstream uses clack log steps
- A `ModelMessage` of the `user` role can carry `Images` (`ModelImage`: the bytes, a media type, and the size), and every provider sends them after the turn's text: an `image_url` part with a data URL for chat completions, `input_image` for Responses, a base64 `image` block for Anthropic, `inlineData` for Google, and an `image` block with its format for Bedrock. The AI SDK builds these parts upstream, so the port writes each provider's shape itself. A model that cannot read images answers with the provider's error, which ends the step with `MODEL_PROVIDER_FAILED`. A judgment sends one when it asks for vision (see [Agents](#agents)); vision on `act` is [not ported](#not-ported). `Pixels.SizeForModel` (internal) caps a screenshot's long side at 768 pixels with upstream's box filter and keeps the scale (image pixels per CSS pixel) in step
- `EngineScreenshot.MaskedRegionCount` counts the regions the engine covered, which upstream carries as `maskedRegionCount` on observed pixels: the web engine counts the secure fields of every frame, and the mobile engine the secure nodes it painted. It is null for an engine that cannot say. A secret fill no longer withholds pixels from a model (upstream #1437 dropped the exposure levels with the pixel taint); the screenshot masks secure fields only.
- `e2e init` writes the model config as a `provider` and `model` (see [Coding agents](#coding-agents)), not a constructed model

## Model usage

Upstream's `ModelUsage` (`agent/usage.ts`) is `ModelUsage` in `Agent/Usage.cs` (internal), the per-step accumulator behind `StepRecorder.AddModelCall` (upstream's `StepAccounting.usage`). `Record` returns the call's tokens, which the `model` event carries as `Count`; `Report` fills `StepModelInfo`, whose `TokenAccounting` and `PeakTokensPerCall` are now real: a call with no usage, or without both token counts, makes the step `adapter-upper-bound`, a negative or oversize count is dropped, a sum past 2^53-1 (`ModelUsage.MaxSafeInteger`) is capped and also marks the step `adapter-upper-bound`, and a cost that is negative, not finite, or whose total overflows is omitted (an overflowed total stays omitted). `BuildReport.ComputeUsage` caps `modelTokens` and `modelCachedTokens` the same way. `ModelUsage.Usage` is upstream's non-exported `Usage` interface; `TokenFields` is upstream's `tokenFields`. Differences: `model-usage.test.ts` is `ModelUsage/ModelUsageAccountingTests` and `ModelUsage/ReportedModelUsageTests`. The third accounting `it` is partial (a C# token count is a `long?`, so `Infinity` cannot be sent). Both integration `it` are partial: the port has no `runExisting` harness or report schema check, the cost is `ModelCallUsage.EstimatedCostUsd` where upstream reads the AI Gateway metadata, the first test sets the step tokens to the maximum directly (a `ModelCallUsage` count is an `int`), and the second sends `-1` only (not `0.5` or `NaN`). The agent's session totals (`E2ESession.InputTokens`) stay `int`.
